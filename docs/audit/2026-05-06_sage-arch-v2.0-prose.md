# SAGE: Salience-Aware Graph Engine

## Architecture Reference Document

**Version:** v2.0
**Date:** May 6, 2026

---

# 1. Introduction

SAGE (Salience-Aware Graph Engine) is a local-first, AI-agnostic knowledge infrastructure system that provides structured, persistent memory for AI-assisted workflows. It combines semantic search, a typed relationship graph, lifecycle state management, and multi-format source ingestion into a unified architecture accessed through a protocol-neutral API.

SAGE addresses a fundamental limitation of current AI workflows: every new session starts from zero. By maintaining persistent, graph-structured knowledge with semantic access, SAGE enables AI clients to discover relevant context, respect source authority boundaries, and build on prior work without re-ingesting or re-explaining the corpus.

The system ingests content from multiple source types (Markdown files, Word documents, PDFs, spreadsheets, and other formats) through pluggable source adapters that produce indexable projections. These projections are stored, chunked, and embedded for retrieval. Relationships between documents are first-class graph edges, enabling traversal, blast radius assessment, and precondition checking. A semantic abstract is generated for every document at ingestion to provide document-level orientation that complements the chunk-level retrieval the projection supports.

SAGE is designed for phased deployment. It runs entirely on a single machine with no external dependencies in its initial phase, using embedded databases for both content storage and graph storage. The storage abstraction layer enables migration to cloud-hosted databases without changing the Core API or client integrations. Phase 1 is the live deployment: SAGE operates in production use against multiple working vaults, with the LanceDB content store, the nomic-embed-text embedding provider, and the Qwen3 abstraction provider in service, and the MCP and REST surfaces operational.

## 1.1 Design Principles

- **Salience over volume.** Retrieve what matters, suppress what does not. Every design decision optimizes for signal-to-noise ratio in retrieval results.

- **Graph-native relationships.** Document identity, version lineage, source authority, and cross-references are first-class graph edges, not naming conventions or folder structures.

- **Multi-source ingestion.** Content enters SAGE from diverse native formats through pluggable source adapters. The system indexes everything without requiring format standardization.

- **Intentional ingestion.** Documents enter SAGE only through explicit caller invocation. SAGE provides no file watcher, polling loop, or auto-ingest. The caller's intentional act is the auditable signal that something belongs in the canonical record. This is a positive architectural choice rather than a deferred design question (CAS-ADR-018).

- **Flexible deployment.** Runs entirely on a single machine with no external dependencies. Deployable to cloud infrastructure when collaboration or scale demands it.

- **AI-agnostic access.** Any AI client (Claude, ChatGPT, Gemini, future systems) connects through the same Core API via protocol adapters (MCP, REST, future protocols).

- **Governance by design.** Source authority, write permissions, lifecycle transitions, and access control are architectural features, not conventions enforced by instructions.

# 2. Conceptual Foundations

## 2.1 From Associative Memory to Operational Knowledge Graph

SAGE draws on the concept of associative memory: retrieving data by content similarity rather than by address or key. Vector embeddings enable this. Each chunk of text is mapped to a point in high-dimensional space where proximity represents semantic similarity. But pure vector search is insufficient for operational use. It lacks structure: version history, authority boundaries, and lifecycle state are invisible to a similarity metric.

The resulting system is an operational knowledge graph with semantic access. The vector layer enables finding things by meaning; the graph layer enables knowing what those things are, where they came from, and how they relate to each other.

## 2.2 The Object-Storage Separation Pattern

Each document's identity, metadata, relationships, and lifecycle state live in the database. The source — whether a Markdown file, Word document, or PDF — lives in the file system or external location. SAGE indexes but does not own the source. Key implications:

- Sources can live anywhere the system can read them: local directories, shared drives, cloud storage, or external systems.
- Physical source location is irrelevant to document identity.
- The application and AI clients are the interface; the file system is invisible infrastructure.
- An AI client and the human application are two interfaces to a corpus of objects stored in a vault (see Section 3.5).

## 2.3 Multi-Source Ingestion and Indexable Projections

Real-world knowledge work produces artifacts in diverse formats. Markdown files orchestrate work. Word documents are formal deliverables. PDFs arrive as reference material. Spreadsheets carry tabular data. A knowledge system that requires format standardization creates friction; one that indexes native formats reduces it.

SAGE addresses this through the concept of the indexable projection. Every source has an original representation (the .docx, the .pdf, the .md, the .xlsx) and a projected representation: structured plain text with heading hierarchy metadata that the chunking and embedding pipeline can process uniformly.

The ingestion pipeline is therefore three-stage. **Stage 1 (Projection):** a source adapter reads the native format and produces structured text. **Stage 2 (Indexing):** the chunking and embedding pipeline operates on the projection, independent of source format. **Stage 3 (Abstraction):** a local LLM generates a density-proportional semantic abstract from the projection metadata and chunk embeddings. This separation means adding a new source type requires only a new adapter, not changes to the indexing or abstraction pipelines.

The semantic abstract serves multiple consumers. Retrieval uses it as a document-level relevance prior in two-pass abstract-boosted search. Steward and orchestrator agents use it as a pre-built summary for orientation queries that do not require the full document. And the abstract is the document-level relevance card an autonomous agent uses to decide, after discovering the document via an MCP discovery tool, whether to fetch the full document. The prompt that generates the abstract is shaped specifically for this triage role: descriptive third-person framing rather than research-paper-shaped narration, with the document's `doc_type` as a parameterized input and explicit anti-fabrication clauses (CAS-ADR-020).

Projections are stored in the database (not as intermediate files) to maintain a single source of truth and avoid staleness from orphaned conversion artifacts.

## 2.4 Relationship to Existing Systems

SAGE occupies a distinct position relative to existing tools in this space:

| System | Similarity to SAGE | Key Difference |
|---|---|---|
| Obsidian | Local-first, file-based knowledge management | SAGE adds vector search, typed graph edges, multi-format ingestion, and AI-native access |
| RAG pipelines | Vector search over document chunks | SAGE adds graph structure, lifecycle management, governance, and multi-source adapters |
| Knowledge graphs (Neo4j, etc.) | Typed relationships between entities | SAGE combines graph structure with vector search and manages document-level objects, not entity-level triples |

# 3. System Architecture

## 3.1 Architectural Layers

SAGE consists of five interlocking layers:

1. **Client Layer.** Protocol adapters for AI clients (MCP, REST), plus the human-facing application.
2. **Core API.** The unified interface exposing all operations: discovery, organization, ingestion, graph traversal, precondition checking, and access control.
3. **Object Model.** The domain layer: source objects, typed graph edges, vault boundaries, the lifecycle state machine, and the three-tier metadata model.
4. **Source Adapter Layer.** Pluggable adapters that read source formats (Markdown, Word, PDF, XLSX, future formats) and produce indexable projections for the content store.
5. **Storage Abstraction Layer.** A unified interface over two logical stores (content store and graph store) that can be backed by different database engines at different deployment phases.

## 3.2 Deployment Model

SAGE is designed for phased deployment. The storage abstraction layer is the critical architectural feature enabling this: the Core API and all client integrations remain unchanged as underlying storage moves from embedded to hosted.

### 3.2.1 Phase 1: Local (Single Machine)

All components run on a single machine. LanceDB (embedded) backs the content store. SQLite backs the graph store. One or more vaults reside on the local file system. AI clients connect via MCP either over stdio or, more commonly in current operation, through a small `mcp-remote` bridge that translates MCP into Server-Sent Events against a local FastAPI server.

In Phase 1, the SAGE Core API and the CAS Application backend run together in a single uvicorn process serving a single port. The two components share an in-memory vault registry and the same SAGE service instances. The MCP transport is mounted on the same FastAPI application. This single-process topology is described in detail in Section 3.5.2; its forward-compatibility properties (Phase 2 separation onto distinct processes or machines) are preserved by structuring the code as if the components communicated over HTTP.

### 3.2.2 Phase 2: Hybrid (Cloud + Local)

Shared vaults move to cloud infrastructure. The Core API for shared vaults runs as a hosted service. Team members connect via MCP over SSE or streamable HTTP. Personal vaults can remain local. The CAS Application backend separates from the SAGE Core API at this point, and the boundary that has existed in code structure since Phase 1 (separate URL prefixes, no shared in-memory state at the API surface) becomes a network boundary.

### 3.2.3 Phase 3: Mature Multi-Tenant

Server-grade databases replace embedded stores for the cloud instance. PostgreSQL replaces SQLite for the graph store; pgvector or Qdrant replaces LanceDB for the content store. The Core API is unchanged; only the storage adapter implementations differ.

## 3.3 Storage Architecture

### 3.3.1 Storage Abstraction Layer

The Core API interacts with two logical stores through abstract repository interfaces. Each store has a single responsibility:

| Store | Responsibility | Phase 1 Backing | Phase 2+ Backing |
|---|---|---|---|
| Content Store | Vectors, full-text index, projections, chunk-level metadata | LanceDB (embedded) | LanceDB on attached storage, pgvector, or Qdrant |
| Graph Store | Document identity, edges, lifecycle, document-level metadata | SQLite | PostgreSQL |

The repository interfaces expose operations (store chunk, query by vector similarity, create edge, traverse graph) without exposing database-specific syntax or connection management.

Transaction granularity is defined at the repository interface level: each Core API operation maps to a single transaction against the relevant store(s). The graph store uses a thread-local connection pool backed by a bounded `ThreadPoolExecutor` (configurable maximum, default four workers), with WAL mode and foreign keys enabled. Each pool thread holds its own connection. The bounded pool with thread-local connections is required because a single shared connection multiplexed across asyncio's default thread pool produces contention under concurrent access between background pipeline tasks and request handlers.

### 3.3.2 Content Store

The content store holds three categories of data: embedding vectors (for semantic search), full-text content (for BM25 keyword matching), and chunk metadata. Chunk metadata includes the chunk's parent document identifier, its heading position within the document, and a denormalized copy of the document's `doc_type`. The denormalized `doc_type` enables `doc_type`-pre-filtered searches at the content store layer rather than as a post-rank filter; this matters because all-archived or all-wrong-type top-K results would otherwise produce empty result sets after post-rank filtering, even when many candidate documents satisfy the user's filter.

### 3.3.3 Graph Store

The graph store holds document identity records, typed directed edges, lifecycle state, and the three tiers of metadata (see Section 4.4). It supports recursive traversal for operations like blast radius assessment, precondition checking, and version-chain walks.

The flexible metadata store (Tier 3, source-type-specific fields) uses a structured key-value representation. Queries against Tier 3 fields use the graph store's native JSON or key-value functions.

### 3.3.4 Phase 1 Implementation

**LanceDB (content store):** Embedded, on-disk columnar store with native vector search, BM25 full-text search, and hybrid fusion. Handles both embedding vectors and full-text indexing in a single engine, eliminating the need for a separate full-text search system. Vault-rewrite operations (re-indexing, large bulk-update sweeps) require explicit `table.optimize()` to merge fragments and reclaim space; without it, fragments accumulate and disk usage can grow by orders of magnitude. `IngestionService.ingest()` does not invoke compaction on the per-document write path; periodic compaction is an operational responsibility documented in the Deployment Model.

**SQLite (graph store):** Embedded relational database with recursive CTE support for graph traversal (used by `traverse`, `chain`, and the supersedes lineage walks performed by the resolver), JSON functions for flexible metadata (Tier 3), and ACID transactions for lifecycle state changes. The entire graph for a vault fits in a single file, supporting the vault-as-directory portability model.

### 3.3.5 Embedding Model

SAGE uses **nomic-embed-text v1.5** via `sentence-transformers`, producing 768-dimensional L2-normalized vectors. The model runs on CPU with `max_seq_length=2048` and `batch_size=8` to avoid contention with the abstraction model's MLX/MPS unified-memory footprint on Apple Silicon. These tuning parameters are not arbitrary: at the default `max_seq_length=8192` the attention matrix grows quadratically and competes with the abstraction model's working set. The current values are the smallest configuration that preserves embedding quality on the project's representative document set without forcing model swap-out under bulk ingest.

### 3.3.6 Chunking Strategy

Projections are chunked by heading hierarchy rather than arbitrary token windows. Each chunk inherits its full heading ancestry as metadata, enabling retrieval results that carry structural context (for example, "Section 3.2 > Implementation Details > Error Handling").

This strategy applies uniformly to all source types. Source adapters are responsible for producing structured text with heading markers; the chunking pipeline consumes that structure regardless of original format.

### 3.3.7 Indexing

At scale (tens of thousands of vectors), SAGE creates an IVF-PQ index (Inverted File Index with Product Quantization) in LanceDB for faster approximate nearest-neighbor search. Below this threshold, brute-force search is sufficient and avoids index maintenance overhead.

The chunks schema in LanceDB carries a `doc_type` column populated at indexing time and kept in sync with the graph store's `doc_type` field through `MetadataService.update_metadata`. This denormalization enables the `doc_type` pre-filter described in §3.3.2; absent it, document-level type filtering would have to be applied as a post-search operation against the top-K, which produces empty result sets when the top-K happens to contain only chunks of the wrong type.

Indexing is on-demand only. There is no file watcher, no polling loop, and no scheduled batch. New documents enter the index when the caller invokes ingest; modified documents enter the index when the caller re-ingests their source path (CAS-ADR-018).

## 3.4 Source Adapter Architecture

### 3.4.1 Ingestion Pipeline

Ingestion proceeds in three sequential stages with clean interface boundaries between them. All three stages complete before `ingest()` returns to the caller, with the document's `pipeline_status` field tracking progress through `projection_complete` → `indexing_in_progress` → `indexing_complete` → `abstraction_in_progress` → `abstraction_complete`. Failure or graceful skip yields `failed` or `abstraction_skipped` respectively. The pipeline is sequential because concurrent in-flight documents would exhaust the local memory envelope: the embedding model, the abstraction model's KV cache, and per-document working state must each fit alongside the operating system, the development environment, and any other processes the user has running. Sequential semantics keep peak memory bounded by the largest single-document working set rather than scaling with batch concurrency.

The three stages:

1. **Projection.** A source adapter reads the native format and produces structured text with heading hierarchy metadata. The projection is stored as a TEXT column on the document record (see Section 4.1). Provenance fields are captured at this stage: `source_content_hash`, `adapter_version`, `projected_at`, and `source_modified_at` (the source file's filesystem modification time, captured during projection).

2. **Indexing.** The chunking and embedding pipeline operates on `projection_text`. It splits by heading hierarchy, enforces chunk size limits, generates embeddings, and stores chunks in the content store with denormalized `doc_type` for pre-filter support.

3. **Abstraction.** A local LLM generates a `semantic_abstract` for the document. The abstract's target length is proportional to the document's information density, calculated from three inputs: source token count, structural complexity (heading depth and section count from the projection), and semantic variance (average pairwise distance between chunk embeddings from the indexing stage). This stage is vault-configurable and degrades gracefully: if the LLM is unavailable, ingestion completes without the abstract and flags the document `abstraction_skipped` (CAS-ADR-011). The abstraction model is loaded lazily on first invocation rather than at service startup; vaults that have not yet generated an abstract incur no abstraction-model RAM cost. Lazy loading is required because the abstraction model is the single largest in-memory tenant and pre-loading it would exclude smaller workflows from the development machine entirely.

The interface boundary between projection and indexing is the projection text: structured plain text with heading markers. Any source adapter that produces valid projection text can participate in the indexing pipeline without modification. The interface boundary between indexing and abstraction is the set of chunk embeddings plus projection metadata; the abstraction stage consumes these to calculate density and generate the abstract.

The pipeline includes one additional pre-projection step on macOS: when SAGE copies a source file into a vault from outside the vault's `storage_root`, it strips UI-layer invisibility markers (described in §3.4.8). This step has no analogue on other platforms; it is a no-op on Linux and Windows.

### 3.4.2 Adapter Interface Contract

Each source adapter implements a common interface:

1. **Input.** A source path (local file) or URI (external system reference), plus adapter-specific configuration.
2. **Output.** Structured text with heading hierarchy markers, the source-type-specific metadata (Tier 3 fields), and optionally a list of adapter-contributed tags namespaced by adapter name (for example, `pdf:scanned`, `pdf:truncated`, dotx style-surface tags).
3. **Contract.** The adapter must produce valid structured text or raise an error with a diagnostic message. Partial extraction is not permitted.

Adapter-contributed tags merge into the document's `tags` field at ingest. On force re-ingest, tags carrying any of the adapter's declared `adapter_tag_prefixes` are stripped before the new tags are merged, preventing stale adapter tags from accumulating across re-ingestions.

### 3.4.3 Phase 1 Adapters

The current production adapter set:

- **Markdown adapter.** Pass-through. Reads the .md file and stores its content as the projection. Heading hierarchy is parsed from Markdown heading markers.
- **Word .docx adapter.** Extracts paragraph text with style-based heading levels via `python-docx`. Maps Word paragraph styles (`Heading 1` through `Heading 9`) to heading hierarchy markers in the projection. Includes a numbering engine that computes rendered heading number prefixes (decimal, upperRoman, lowerRoman, upperLetter, lowerLetter) with counter reset on parent-level increment, table extraction as pipe-delimited text rows, and cross-reference field resolution via cached display values.
- **Word .dotx template adapter.** Extension overload of the docx adapter. For .dotx files, emits a `template_style_inventory` (Tier 3 metadata) carrying structured numbering details for templates only. Adapter-contributed tags surface custom-only style tags and all-styles numbering tags.
- **XLSX adapter.** Multisheet projections. Heading paths reflect sheet names and within-sheet groupings. Column headers are surfaced in content. Preview rows are configurable per vault. Content hash is computed from the raw bytes of the source file.
- **PDF adapter (v0.1).** Native-text only via `pdfplumber` (text extraction) and `pypdf` (outline and Info-dictionary reading). Outline-or-flat heading strategy: PDFs with a bookmarks outline produce nested heading nodes via outline-entry page ranges (depth capped at 10, deeper entries dropped with text preserved in the nearest ancestor's content); PDFs without an outline produce a single flat level-1 heading covering the full extracted text. Title resolution priority chain: `/Info /Title` → first outline entry → first body line of 120 characters or fewer → filename stem. Scanned-PDF detection via `total_chars==0` heuristic; image-only PDFs emit empty projection with a `pdf:scanned` adapter tag and route to `abstraction_skipped`. OCR is explicitly out of scope for v0.1; users OCR scanned PDFs externally and re-ingest.
- **Obsidian adapter (planned).** Obsidian stores content as plain Markdown files in a local directory, making integration trivial through the existing Markdown adapter. The wikilink syntax is a candidate source for edge inference during ingestion.

### 3.4.4 Projection Persistence

Projections are stored in the database (a `projection_text` field on the document record). No intermediate Markdown or text files are generated. This ensures that the indexed content and the stored projection are always in sync.

A Core API operation, `export_projection(document_id, output_path)`, writes the stored projection to a Markdown file on demand for inspection or debugging.

Stored projections also serve as the re-chunking source: if the chunking strategy or embedding model changes, the system can re-chunk and re-embed from stored projections without re-running source adapters.

When a caller re-ingests a known path and the source has changed (detected via hash comparison; see Section 3.4.5), SAGE runs the adapter against the new source, stores the new projection on a new document record, creates a `supersedes` edge from the new version to its predecessor, transitions the predecessor to `archived`, and re-chunks and re-embeds from the new projection. The prior projection is retained on the superseded document record.

### 3.4.5 Source Change Detection

SAGE indexes but does not own source files. Sources have a life independent of SAGE; the system records provenance at ingestion and detects change only when a caller re-ingests a known path. Three capabilities support this model:

1. **Provenance capture.** At ingestion, SAGE records provenance fields on the document record: `source_content_hash` (SHA-256 of the source file content), `adapter_version` (version of the adapter that produced the projection), `projected_at` (timestamp of the ingestion), and `source_modified_at` (the source file's filesystem modification time at ingestion).

2. **Hash-comparison change detection on re-ingest.** When a caller invokes `sage_ingest`, `app_scan_directory`, or `app_batch_ingest` against a known path, SAGE re-runs the source adapter and compares the new content hash against the stored `source_content_hash`. If they match, the existing document record is unchanged. If they differ, the path's content has changed since the last ingest.

3. **Versioned re-ingestion.** When change is detected, SAGE creates a new document record with the new projection, creates a `supersedes` edge from the new version to the prior version, transitions the prior version to `archived`, and re-chunks and re-embeds from the new projection.

There is no file watcher, no polling loop, and no scheduled scan. The caller's intentional act, invoking ingest, is the auditable signal that something belongs in the canonical record. The architectural rationale, recorded as CAS-ADR-018, is that automatic ingestion would shift the trust boundary (the file would commit itself rather than the caller committing it), expand SAGE's runtime surface to include long-running watcher subscriptions and cross-platform filesystem-event handling, and invite spurious ingestion events from partial writes, editor swap files, and cloud-sync transients. The CAS Application's directory-scan workflow provides the convenience that watching would offer (drop files into a directory, then click Scan) without any of these costs. Future reintroduction of file watching, if ever desired, requires a superseding ADR.

### 3.4.6 Metadata Extraction

Source files often carry metadata in multiple locations: filename conventions, document content, YAML frontmatter, or PDF document properties. SAGE provides filename-based extraction as a built-in capability and accepts authoritative metadata directly from the caller. The boundary between these two paths is governed by an explicit per-call flag.

**FilenameParser as a SAGE-provided library.** A vault's `metadata_extraction.filename_extraction` configuration can declare a filename pattern with date, version, project, code, and title segments, plus a `code_to_doc_type` map and a `keyword_to_doc_type` map for resolving filename codes and keywords to the vault's `doc_type` enum. SAGE provides a tolerant parser that extracts these segments. The parser lives in SAGE rather than in the application backend so that filename-based extraction runs uniformly across all ingestion entry points (CAS-ADR-015). Callers may invoke the parser without performing an ingest via the Core API endpoint `POST /sage_vaults/{vault_id}/parse-filename` and the corresponding MCP tool `sage_parse_filename`. Both return parsed metadata and have no side effects.

**Caller authority via `needs_review`.** A document record carries a `metadata_confirmed` boolean: when `true`, the document's metadata is treated as confirmed; when `false`, it appears in the pending-metadata feed for human review. The `IngestRequest` carries a corresponding `needs_review: bool` field with default `false` that controls how SAGE sets `metadata_confirmed` at ingest. The semantics differ depending on the request value:

- **`needs_review=false` (default).** SAGE commits caller-supplied metadata as authoritative. It does not invoke filename inference. It does not mark the document `metadata_confirmed=false`. The caller is responsible for any metadata derivation that would have come from filename parsing; the typical pattern is for the caller to invoke `parse_filename`, present suggestions to a human or apply program logic, and pass the resulting values in the `IngestRequest.metadata` field.
- **`needs_review=true`.** SAGE marks the document `metadata_confirmed=false` (causing it to appear in the pending-metadata feed for review) and may invoke filename inference to populate fields the caller did not supply.

The default-`false` choice reflects the empirical pattern: the dominant ingest source in current operation is agents calling SAGE directly with authoritative metadata. The bulk-ingest workflow in the CAS Application is the principal `needs_review=true` consumer; it sets the flag explicitly on every ingest call so its review queue continues to populate under the new default.

**Precedence chain.** When caller and inference both produce a value for the same field, the precedence is: caller-supplied value > filename parse (only when `needs_review=true`) > chain inheritance (described next) > vault default. Caller values always win on a per-field basis; the chain-inheritance and inference paths fill only the fields the caller omitted.

**Chain inheritance for type-shaped fields.** When `IngestRequest.supersedes_document_id` is set, SAGE reads the predecessor document's `doc_type`, `project`, and `authority_scope`. For each of these three fields, if the caller did not supply a value, the predecessor's value is applied to the new document. These three fields share a common property: they describe what kind of document this is or where it sits in a workflow, and they are typically stable across a `supersedes` chain. Reading them from the predecessor at ingest is a graph-state operation that depends on chain context only SAGE owns; it is not pattern matching against caller-defined rules. Caller-supplied values continue to win on a per-field basis.

Fields excluded from chain inheritance: `title`, `version_label`, and `document_date` (definitionally version-specific) and `tags` (set semantics with normal editorial drift across a chain make "inherit" ambiguous: union, replace, or skip are all reasonable defaults). Callers that wish to carry tags across a chain transition do so deliberately by supplying them in the new ingest.

The architectural rationale for the caller-authoritative model is recorded as CAS-ADR-021. It follows from two standing principles: SAGE indexes everything and owns nothing (so vault-specific filename heuristics, which encode caller opinions about how filenames map to metadata, do not belong inside SAGE's ingest pipeline); and the boundary rule (caller-side concerns sit above SAGE). The vault config option `metadata_extraction.review_required` is not part of the schema; review semantics are caller-driven via `IngestRequest.needs_review`.

### 3.4.7 Edge Inference

During bulk ingest, edges between newly ingested documents and existing vault documents can be inferred from filename conventions. Edge inference operates in three tiers based on the cost of false positives. Tier assignments and inference rules are vault-configured. The inference engine itself runs in the application backend (`app/backend/edge_inference.py`); SAGE provides the link primitive and the staging table that the engine writes to. This boundary is deliberate: filename-pattern inference is a caller-side concern that varies by domain, while the graph-state operations it produces (link, staging insert) are SAGE's.

**Tier 1: Auto-create.** Edges created directly in the production graph without human review, restricted to cases where inference is deterministic. The `supersedes` chain produced by version-detection during bulk ingest is the principal Tier 1 consumer. Each new version supersedes its immediate actual predecessor in the chain, not all prior versions. The chain is therefore linear by construction: v3 supersedes v2, v2 supersedes v1, with no edges from v3 directly to v1. Linear chain semantics simplify the resolver, prevent the edge count from growing as the square of chain length, and align with the natural mental model of version history.

**Tier 2: Auto-suggest.** Edges placed in a staging table for human review. The CAS Application surfaces suggested edges grouped by type for confirmation or dismissal. Currently active Tier 2 inference: `covers` edges (workflow-to-content based on shared filename codes; for example, a checklist whose filename contains a patent code creates a candidate `covers` edge to the corresponding patent draft). Deferred to future work: `bundles_with` edges via filename co-location (requires a ZIP adapter), `references` edges from textual cross-reference detection.

**Tier 3: Manual only.** Edges that carry governance or workflow semantics requiring human or agent judgment: `authoritative_for`, `depends_on`, and `sync_target`. These are created via explicit `link()` calls and never inferred.

**Mechanical-vs-curated provenance gate.** Auto-inferred `supersedes` edges carry a leading `[version_chain]` marker on the edge's `rationale` field, set at creation time. This marker enables a discipline that protects reviewer judgment from mechanical overwrite: when a chain repair operation (triggered by an out-of-order version arrival that requires reshaping the chain) computes a candidate set of edge removals, it inspects the rationale of each candidate. If every removal candidate carries the prefix, the repair executes as Tier 1 (auto unlink and re-link). If any removal candidate is hand-curated (lacks the prefix), the entire group's repair downgrades to Tier 2 staging, and the conflicting hand-curated edge remains in the production graph untouched. Group-level downgrade reflects the observation that a chain is a coherent structure: applying part of a repair while leaving the rest for review produces neither the prior state nor the desired state, and surfaces an incomplete proposal to the reviewer.

The trust direction is consistent with the broader architectural principle: humans correct the engine; the engine never silently corrects humans. Auto-inferred edges are mechanical conclusions from filename metadata that the engine can re-derive at any time. Hand-curated edges encode reviewer judgment that the engine has no way to reproduce. The provenance gate keeps the engine free to update its own prior conclusions while protecting reviewer judgments by default. The design rationale is recorded as CAS-ADR-019.

The staging table uses the same schema as the production edge table. Confirmed suggestions are moved to the production edge table; dismissed suggestions are deleted. All graph operations (`traverse`, `chain`, `check_preconditions`, blast radius assessment) query exclusively against the production edge table, ensuring the confirmed graph is clean by construction rather than by query discipline.

### 3.4.8 UI-Layer File Metadata Normalization

When SAGE copies a source file into a vault from outside the vault's `storage_root`, a sanitization pass strips UI-layer invisibility markers from the destination. On macOS, this clears the BSD `UF_HIDDEN` chflag and the invisible bit (0x40 in byte 8) of the `com.apple.FinderInfo` extended attribute, preserving all other Finder metadata (color labels, type and creator codes, stationery flags, Spotlight tags). The helper is a no-op on non-macOS platforms.

The rationale, recorded as CAS-ADR-016, is that UI-layer invisibility encodes source-artifact semantics ("this is the agent's scratch, hide it from the user"), not canonical-artifact semantics ("the user will audit this"). The vault is the canonical state substrate; its artifacts are user-auditable by contract. Propagating an agent's source-artifact UI intent to the canonical artifact is a category error. The boundary is the same one motivating CAS-ADR-015: properties that SAGE's contract guarantees must be enforced at the SAGE layer, not delegated to caller discipline.

Errors during sanitization are swallowed: UI-layer normalization is best-effort and must not fail an ingest. Future UI-layer metadata mechanisms (quarantine flags, additional Finder attributes) are evaluated under the same principle.

## 3.5 Client Access Architecture

### 3.5.1 Protocol Adapters and Transports

SAGE exposes a protocol-neutral Core API. Thin adapters translate each client protocol into Core API calls; the Core API never changes because a new client type connects.

| Client | Protocol | Transport | Use Case |
|---|---|---|---|
| AI client (MCP) | MCP tools | SSE via `mcp-remote` bridge to the FastAPI server's `/mcp/sse` mount (current default); stdio (legacy) | AI-assisted workflows |
| AI client (REST) | REST | HTTP | Alternative AI clients |
| CAS Application | REST | HTTP via the application backend (single process in Phase 1) | Browsing, organizing, oversight |
| Future clients | Any protocol | Protocol adapter | Extensible by design |

The MCP transport choice deserves a note. SSE transport mounts FastMCP's SSE app on the FastAPI server at `/mcp`, and the AI client uses a small `mcp-remote` bridge (`npx mcp-remote@latest`) as a stdio-to-SSE adapter. The bridge process is lightweight; the heavyweight SAGE state (model weights, database connections, vault registry) lives once in the FastAPI process and is shared across REST callers, MCP callers, and the CAS Application backend. A standalone-stdio mode is also supported for clients that cannot use the SSE bridge, but launching a separate Python process per MCP client duplicates the embedding model, vault services, and SQLite connections, so the SSE-mounted form is preferred whenever possible.

### 3.5.2 Single-Process Topology

In Phase 1, a single uvicorn process serves four interfaces:

- The SAGE Core API at the URL prefix `/sage_vaults/*`.
- The CAS Application backend at the URL prefix `/app/*` (covering `/app/scan` and `/app/ingest`).
- The CAS Application's React SPA as static assets at the root path.
- The FastMCP SSE transport at `/mcp`.

All four share the same FastAPI application object, the same `app.state.vault_registry` (a dictionary keyed by vault id), and the same SAGE service instances (one set of `IngestionService`, `RetrievalService`, `GraphOpsService`, etc., per vault). The vault registry pattern matches the topology that the MCP server used from its inception, which made the unification straightforward.

Despite the shared in-memory state, the code is structured as if the components communicated over HTTP. The CAS Application backend never imports SAGE service classes directly; it goes through the SAGE Core API surface. The URL-prefix boundary (`/app/*` versus `/sage_vaults/*`) is enforced by tests; the OpenAPI specifications (`sage_core_api.openapi.yaml` and `cas_app_api.openapi.yaml`) are separate documents reflecting the architectural separation. This forward-compatibility choice means that Phase 2 separation, when it occurs, is a deployment change rather than a code change: the CAS Application backend can be moved to its own process or its own machine, communicating with the SAGE Core API over HTTP, without requiring the kind of refactor that would be needed if the components shared in-memory state through direct method calls.

The single-process topology is a Phase 1 architectural choice rather than a degenerate accident of co-location. The forward-compatibility properties (URL-prefix boundary, separate OpenAPI specifications, no direct cross-component imports) are part of the architecture, not an artifact of how the components happen to deploy.

# 4. Object Model

The Object Model is SAGE's domain layer. It defines the entities the Core API operates on, the relationships among them, and the lifecycle states that govern their transitions. Three observations to keep in mind throughout the section:

- **Documents are the primary entity.** Every other entity in the model exists to describe documents, relate them to each other, control access to them, or track their lifecycle.
- **Edges are first-class.** Relationships between documents are not naming conventions or folder structures; they are typed, queryable rows in the graph store with explicit semantics, optional anchor fields, and (since CAS-ADR-017) declared resolution policies.
- **Some fields are surface-level operational state, not architectural facts.** Fields like `pipeline_status` and `metadata_confirmed` describe where a document is in its processing or review lifecycle; they are not part of the document's content or identity. They are surfaced in the Document record because consumers (agents, the application, the retrieval pipeline) need to observe them, not because they describe what the document is.

## 4.1 Document

The Document is the primary entity. It represents a single source artifact, regardless of native format, with its identity, metadata, relationships, and lifecycle state managed in the graph store.

| Field | Type | Description |
|---|---|---|
| `id` | string | Immutable, assigned at creation (short hash plus a hint derived from the title) |
| `title` | string | Human-readable display name; editable |
| `source_type` | enum | One of `markdown`, `docx`, `pdf`, `xlsx`, `email`, `onenote`, `teams_chat` |
| `source_path` | string | Location of the original artifact: local file path or URI |
| `lifecycle_status` | string | Vault-configurable lifecycle state (see §4.9) |
| `version_label` | string | Human-readable version indicator (`v1`, `v2`, `draft`, `final`, etc.) |
| `project` | string | Project or workstream identifier |
| `tags` | string[] | Freeform tags from caller-supplied metadata, YAML frontmatter, or adapter-contributed tags |
| `authority_scope` | string (nullable) | Content domain this document governs (if authoritative) |
| `doc_type` | string | Vault-configured Tier 2 metadata field (see §4.4.2) |
| `document_date` | string (nullable) | Authoritative content date in `YYYY-MM-DD` format. Derived from filename date code when present, with `source_modified_at` as fallback. Validated at request boundary. |
| `source_content_hash` | string | SHA-256 of the source file content at last ingestion (provenance) |
| `adapter_version` | string | Version of the source adapter used at last ingestion (provenance) |
| `source_modified_at` | timestamp (nullable) | The source file's filesystem modification time at ingestion. Distinct from `created_at`, which is SAGE's ingestion timestamp. Null for non-file sources. |
| `created_by` | FK → User | User or agent that created this document |
| `created_at` | timestamp | Creation time (SAGE ingestion timestamp) |
| `updated_at` | timestamp | Last modification time |
| `projected_at` | timestamp (nullable) | Last time the source adapter ran against this source |
| `indexed_at` | timestamp (nullable) | Last time projection was chunked and embedded into the content store. Null until indexing completes; the field is nullable so a document can carry a successful projection while indexing is mid-stage or has failed. |
| `semantic_abstract` | text (nullable) | LLM-generated abstract with density-proportional length; generated at ingestion, regenerated on re-ingestion (CAS-ADR-011); shaped per CAS-ADR-020 for agent relevance triage |
| `metadata_confirmed` | boolean | Set true when caller-supplied metadata is authoritative; false when the document is in the pending-metadata feed for human review (CAS-ADR-021) |
| `pipeline_status` | enum | Current stage of the ingestion pipeline (see §4.11) |
| `pipeline_error` | string (nullable) | Failure description when `pipeline_status` is `failed` |

A reader should note three properties of this table that are not obvious from inspection. First, `created_at` and `source_modified_at` are different timestamps with different meanings: `created_at` is when SAGE ingested the document; `source_modified_at` is when the source file was last modified on disk before that ingest. Second, `document_date` is editorial: it is the date the document is about, not the date the source file was created or modified. The filename parser is the primary source for `document_date`, and `source_modified_at` is the fallback when no filename date is present. Third, `indexed_at` differs from `projected_at` because the pipeline is sequential but the stages can fail independently: a document can have a successful projection (`projected_at` populated) and a failed indexing (`indexed_at` null, `pipeline_status` `failed`).

## 4.2 User

The User entity represents any actor (human or agent) that interacts with SAGE. It serves two purposes: provenance tracking (who created or modified a document) and access control (who is registered as an editor).

| Field | Type | Description |
|---|---|---|
| `id` | string | Immutable, assigned at registration |
| `display_name` | string | Human-readable name |
| `type` | enum | `human` or `agent` |
| `created_at` | timestamp | Registration time |

## 4.3 Editor Model (Access Control)

The editor model governs write access to individual documents.

- A document with no registered editors is open: any registered user can read and modify the document.
- Registering one or more editors on a document restricts write access to that set. All other registered users have read-only access.
- Editor registration is stored as a join table: `document_editors(document_id, user_id, registered_at)`.
- SAGE never deletes documents. Deletion is not a permission level; it is a system invariant (see §6.4).
- Read access is unrestricted within a vault in Phase 1. Read restrictions are a Phase 3 consideration if multi-tenant requirements demand it.

The Core API exposes `register_user`, `set_editors`, and `get_editors` operations for managing this surface. The editor `GET`/`PUT` document endpoints are formally declared in the OpenAPI specification but not yet implemented in code; they are forward declarations awaiting a concrete need from a calling workflow.

## 4.4 Metadata Model

Document metadata is organized into three tiers with different mutability and scope characteristics.

### 4.4.1 Tier 1: Core (Invariant)

Core metadata fields exist on every document record in every vault, regardless of source type or domain. They are used by the Core API for lifecycle management, provenance tracking, retrieval scoping, and ingestion-pipeline observability. The Tier 1 enumeration is the union of fields in the §4.1 table other than `doc_type` (which is Tier 2). It is the same across vaults; it cannot be extended by domain configuration.

### 4.4.2 Tier 2: Vault-Configured

Vault-configured metadata consists of a single field: `doc_type` (enum, vault-defined), which classifies the document within the vault's domain vocabulary. Examples: a document portfolio vault might define `document_draft`, `work_plan`, `checklist`, `glossary`, `audit_report`, `template`, `decision_log`, `correspondence`, and `figure_spec`. A theology vault might define `lecture_notes`, `exegesis`, `sermon_outline`, and `bibliography`. Each vault declares its own enumeration in its `vault_config.yaml`.

The `doc_type` field is structurally Tier 2 but is treated as Tier 1 for operational purposes: it appears on every document record, has a non-null default (`misc` if no other resolution path produces a value), and is denormalized into the chunks schema in the content store to support pre-filtered search.

### 4.4.3 Tier 3: Source-Type-Specific

Source-type-specific metadata captures fields that only make sense for a particular source format. These are stored in a structured key-value representation in the graph store.

| Source Type | Example Tier 3 Fields |
|---|---|
| Markdown | `yaml_frontmatter` (parsed key-value pairs from YAML header) |
| Word `.docx` | `word_styles` (list of heading styles used), `paragraph_count`, `has_track_changes` |
| Word `.dotx` | `template_style_inventory` (structured numbering details for templates only) |
| XLSX | `sheet_count`, `sheet_metadata`, `dimensions` |
| PDF | `page_count`, `pages_extracted`, `pdf_version`, `has_outline` |
| Email | `from`, `to`, `cc`, `subject`, `date`, `thread_id`, `has_attachments` |
| OneNote | `notebook`, `section`, `page_title`, `last_modified_by` |

## 4.5 Edge (Graph Relationship)

Edges represent typed, directed relationships between Documents. They are stored in the graph store and are traversable via the Core API.

| Field | Type | Description |
|---|---|---|
| `id` | UUID | Auto-generated at edge creation; enables disambiguation when duplicates are emitted by inference |
| `source_id` | FK → Document (nullable) | Origin document; nullable to accommodate `retracts` edges, which target an edge instance rather than a document pair |
| `target_id` | FK → Document (nullable) | Target document; nullable for the same reason |
| `edge_type` | enum | One of the eleven values in §4.6 |
| `resolution_policy` | enum | One of `none`, `transitive_source`, `transitive_target`, `transitive_both`, `TBD`. Frozen at edge creation from the vault's edge-type registry; later registry edits do not retroactively change resolution behavior for existing edges (CAS-ADR-017) |
| `source_valid_from_version` | FK → Document (nullable) | Anchor on the source chain: the document_id that identifies the chain member from which this edge becomes valid going forward. Required when `resolution_policy` is `transitive_source` or `transitive_both`. Forbidden for transitive_target edges. `Retracts` edges carry `policy: none` but overload this field to identify the retracting chain and the version from which the retraction takes effect |
| `target_valid_from_version` | FK → Document (nullable) | Anchor on the target chain. Required when `resolution_policy` is `transitive_target` or `transitive_both`; forbidden otherwise |
| `valid_until_version` | FK → Document (nullable) | Tombstone marker used exclusively for merge-triggered edge retirement. Set on the edge at the terminal predecessor version when a chain merge occurs |
| `retracted_edge_id` | UUID (nullable) | Used only on `retracts` edges to identify the edge instance being retracted |
| `created_at` | timestamp | When the relationship was established |
| `notes` | string (nullable) | Optional annotation on why the relationship exists |
| `rationale` | string (nullable) | Why this relationship exists or why this transition occurred. Particularly valuable on `supersedes` edges for capturing decision context. Auto-inferred edges authored by version-chain inference carry a leading `[version_chain]` marker on this field, which the chain-repair operation uses to distinguish mechanical inferences from hand-curated edges (see §3.4.7 and CAS-ADR-019) |

A write-time invariant gates the anchor fields. The validator inspects `resolution_policy` and refuses any edge whose anchor population does not match the policy: `transitive_source` requires `source_valid_from_version` populated and `target_valid_from_version` null; `transitive_target` is the mirror; `transitive_both` requires both populated; `none` requires both null. `Retracts` edges are a special case of the `none` policy: they require `source_valid_from_version` (the retracting chain anchor) and `retracted_edge_id`, and they forbid `source_id`, `target_id`, and `target_valid_from_version`. The invariant is enforced at the edge-write boundary in `LinkRequest` validation, producing one of four error codes (`EDGE_ANCHOR_POLICY_VIOLATION`, `RETRACT_TARGET_NOT_EDGE`, `MERGED_FROM_VALIDATION`, `TBD_POLICY_EDGE`) on violation.

The schema choice of two separate nullable anchor fields, rather than a tuple-valued field, is deliberate. Every edge row has the same columns regardless of its policy, so the resolver, traversal API, validators, and debug tooling all read the relevant field directly. Standard null semantics handle "not applicable." Predicates like "find all edges whose source anchor is a chain member of X" are indexable column queries rather than JSON-blob lookups. Adding a new resolution policy in the future is schema-additive rather than schema-invasive. And the write-time invariant becomes a declarative table lookup from policy to required fields.

## 4.6 Edge Type Taxonomy

Eleven edge types are defined, grouped by their default resolution policy. A worked example illustrating how the policies compose under the resolver appears in Appendix D.

**Meta-edges (resolution_policy: `none`).** These edges express version-specific facts about lineage state. They do not propagate through anchor fields because they are themselves the anchors that other edges use.

| Edge Type | Semantics | Traversal Use |
|---|---|---|
| `supersedes` | Version lineage: newer replaces older. Created at re-ingest when source content changes, and by Tier 1 inference during bulk ingest with version-detected filenames. Linear: each version supersedes only its immediate predecessor (see §3.4.7) | Walk forward to find the current version of a document |
| `retracts` | Governance-level retraction of an edge instance, anchored on the retracting chain at the version from which the retraction takes effect. One-sided: retraction applies from the anchored chain's side; the counterpart chain is unaffected | Filter edges out of resolution when a retraction is upstream of the query position |
| `merged_from` | Chain-level provenance: source is the first version of a successor chain after a chain merge; target is the terminal version of each predecessor chain. Predecessor-chain edges are tombstoned via `valid_until_version` set at the merge point | Trace chain provenance across merges; predecessor edges do not auto-propagate forward |

**Transitive-source edges (resolution_policy: `transitive_source`).** The source-side endpoint is the chain (anchor on source chain identifies the version from which the edge applies); the target endpoint is a stable artifact.

| Edge Type | Semantics | Example |
|---|---|---|
| `derived_from` | Structural inheritance: one artifact templated from another. Source-anchored because the derived chain may evolve while the template anchors a stable origin | A QA-1 Checklist instance derived_from the Checklist Template |

**Transitive-both edges (resolution_policy: `transitive_both`).** Both endpoints are independently advancing chains; the edge claims a relationship between the two chain identities.

| Edge Type | Semantics | Example |
|---|---|---|
| `instantiated_from` | Live-tracking derivation, similar to `derived_from` but where the source chain is expected to track template evolution | Workflow instance live-tracking its template chain |
| `references` | Loose association; one document cites or depends on another | Decision Log entry referencing the Glossary it cites |
| `covers` | Oversight mapping: one artifact documents, audits, or reviews another | Audit Report covering the document it audits |
| `bundles_with` | Co-traveling artifacts forming a logical unit | Document Draft + Figures + Claims Sheet |
| `depends_on` | Precondition gate: the source document depends on the target being in a valid state | Workflow function depending on its input documents |

**Deferred-policy edges (resolution_policy: `TBD`).** These edges have policies that have not yet been resolved at the SAGE-core registry level. They behave as if `policy=none` (no anchor required, no transitive resolution) until the policy is set.

| Edge Type | Semantics | Example |
|---|---|---|
| `authoritative_for` | Source authority boundary: which document governs this content domain | Glossary authoritative_for terminology |
| `sync_target` | Bidirectional sync relationship; possibly to be folded into `references` after evaluation | Glossary definition sync_target consuming document |

The eleven-row registry plus the resolution-policy enumeration is sufficient to express version-specific facts (the meta-edges), one-sided chain-to-stable relationships (`derived_from`), and chain-to-chain claims that persist across version turnover (the transitive-both group).

## 4.7 Edge Type Registry and Resolution Model

Each vault carries an edge-type registry that assigns a resolution policy to every edge type the vault uses. The registry lives in SAGE core, not in vault configuration: consistent graph semantics across all vaults is more important than per-vault customization. The registry's row for each edge type is read at edge creation, frozen onto the edge row, and never re-read for that edge thereafter. Registry edits affect future edges only.

The resolution policy values are exhaustively four:

- **`none`.** Version-specific edge. The edge is valid at the specific (`source_id`, `target_id`) pair; the resolver does not perform a transitive walk for edges with this policy. Meta-edges (`supersedes`, `retracts`, `merged_from`) carry this policy because they are themselves the lineage facts that other edges' resolution refers to; making them transitive would create a loop. `Retracts` edges are a special case: they carry `policy: none` for resolution purposes (the retraction does not propagate transitively) but overload `source_valid_from_version` to identify the version on the retracting chain from which the retraction takes effect, with `source_id` and `target_id` both null since the retraction's target is an edge instance addressed by `retracted_edge_id`.
- **`transitive_source`.** The source-side endpoint is anchored on a chain via `source_valid_from_version`; resolution accepts any source version downstream of the anchor in the chain's `supersedes` lineage. The target endpoint is stable (no anchor; the edge applies to `target_id` exactly).
- **`transitive_target`.** The mirror of `transitive_source`. Source endpoint stable; target anchored.
- **`transitive_both`.** Both endpoints are anchored. Resolution accepts any source version downstream of `source_valid_from_version` paired with any target version downstream of `target_valid_from_version`.

A fifth value, `TBD`, exists as a governance placeholder for edge types whose final policy has not been decided. Edges with `TBD` policy behave as `none` at resolution time but can be batch-promoted to a final policy via a registry update and a one-time backfill of anchor fields.

**Resolution at query time.** When `sage_traverse` walks the graph, it consults the edge-type registry for each edge encountered. For `none`-policy edges, the edge is included if and only if the query position matches `(source_id, target_id)` exactly. For `transitive_source` edges, the edge is included if the query's source position is downstream of `source_valid_from_version` in the source chain's `supersedes` lineage. The mirror logic applies to `transitive_target`. For `transitive_both`, both anchors must be satisfied.

Retractions are one-sided. A `retracts` edge applies only when the query position is on the retracting chain (the chain identified by the retracts edge's `source_valid_from_version`). Within that scope, if the retraction's anchor is upstream of the query position, the retracted edge is short-circuited out of the result set. Queries from other chains see the retracted edge unaffected. When the edge's `valid_until_version` is set and is upstream of the query position, the edge is tombstoned and similarly excluded. The four resolution events (`anchor_hit`, `anchor_miss`, `retracts_applied`, `tombstone_applied`) are logged to a `resolution_path` debug payload that is populated when `TraverseRequest.debug` is true; this surface is intended for diagnosing why an expected edge did or did not appear in a result set.

**Edges with NULL resolution_policy.** When an edge row carries NULL in its `resolution_policy` column (for example, edges in vault data that pre-dates the registry), the resolver treats `policy IS NULL` as `policy=none`: no anchor required, no transitive walk, and the edge surfaces only at exact `(source_id, target_id)` matches. A data migration that backfills `resolution_policy` and the anchor fields is available to promote such rows to full chain-scoped semantics; the migration is run on demand rather than automatically.

The architectural rationale for chain-scoped resolution, the choice of two separate anchor fields, the distinction between in-chain retractions and merge tombstones, and the worked example of how the primitives compose are recorded in CAS-ADR-017. The Appendix D worked example walks through a representative case.

## 4.9 Lifecycle State Machine

Documents transition through lifecycle states via explicit actions. The set of valid states and transitions is configurable per vault, but a base set is always present:

| From State | Action | To State | Semantics |
|---|---|---|---|
| (new) | `ingest` | `active` | Document enters the system |
| `active` | `supersede(new_version_id)` | `archived` | A newer version replaces this one. A `supersedes` edge from the new version to this document is created in the same transaction |
| `active` | `complete()` | `completed` | Work fulfilled its purpose; no replacement exists |
| `active` | `archive()` | `archived` | Direct archival without supersession |
| `completed` | `archive()` | `archived` | Moved to long-term storage |
| `archived` | `reactivate()` | `active` | Returned to active use (exceptional case) |

The base set does not include a `superseded` lifecycle state. A document being superseded by a newer version transitions directly to `archived`, and the `supersedes` edge from the new version to the archived predecessor carries the version relationship. There is no separate `superseded` state because the information it would carry, namely "an `archived` document for which a `supersedes` edge points elsewhere," is already queryable via the edge.

Vaults that require additional lifecycle states (for example, domain-specific processing pipelines) define them in `vault_config.yaml`. SAGE enforces transition validity by consulting the vault's lifecycle declaration; the orchestration layer (or any caller) determines when to trigger transitions.

The supersede transition is atomic. The graph store provides `supersede_atomic(predecessor_id, predecessor_updates, edge)` which collapses the lifecycle flip and the edge insert into a single SQLite transaction, and `insert_with_supersede_atomic(new_doc, predecessor_id, predecessor_updates, edge)` which extends that to also include the new document's insert. Atomicity is required because separate calls for the lifecycle flip and the edge insert would admit a window in which a partial failure leaves the predecessor with `lifecycle_status=archived` and no `supersedes` edge pointing to a successor (an "orphan" state). The atomic primitive closes the window.

## 4.10 Decision Logs

Stewards and orchestrators may each own a decision log as a SAGE-managed companion artifact. Decision logs capture operational judgment that does not produce an artifact revision: decisions not to act (a steward evaluates a potential change and concludes no change is warranted), decisions deferred (an issue is identified but resolution depends on something outside the steward's scope or the timing is not right), and cross-artifact reasoning (an orchestrator's rationale for coordinating a multi-artifact operation in a specific sequence).

Decision logs are append-only. Revised judgments are recorded as new entries with a back-reference to the superseded entry, paralleling the supersession pattern used for documents. Domain instantiations determine which agents receive decision logs, since not every steward accumulates judgment worth recording. The schema for decision-log entries is defined in the Formal Substrate (`docs/fs/sage/decision_log.schema.json`); it covers the three entry categories above with structured fields for the entry's subject, the judgment recorded, and the back-reference (if applicable) to a superseded entry.

The architectural rationale for placing decision logs inside SAGE rather than in a separate memory system is recorded in CAS-ADR-012. The single-substrate property is load-bearing: a parallel memory system would split the steward's accumulated judgment across two stores and force synchronization between them. Append-only semantics mirror the steward mutation governance model and prevent accidental loss of judgment history.

The schema is defined in the Formal Substrate, but no vault has yet provisioned a live decision-log artifact. The first consumer (a domain steward) awaits domain-instantiation choices about which agents accumulate judgment of the kind decision logs are designed to capture. Orchestrator decision logs await ROOT Harness implementation; until ROOT Harness exists, there are no orchestrator agents to own them.

## 4.11 Pipeline Status

A document's `pipeline_status` field tracks its progress through the ingestion pipeline:

| Status | Meaning |
|---|---|
| `projection_complete` | Source adapter has produced the projection; chunking and embedding have not started |
| `indexing_in_progress` | Chunks are being embedded and written to the content store |
| `indexing_complete` | Chunks are persisted; abstraction has not started |
| `abstraction_in_progress` | The abstraction model is generating the document's `semantic_abstract` |
| `abstraction_complete` | All three pipeline stages finished successfully |
| `abstraction_skipped` | Abstraction was disabled for this vault, or the abstraction model was unavailable; ingestion completed without an abstract (CAS-ADR-011 graceful degradation) |
| `failed` | A pipeline stage failed; `pipeline_error` carries the diagnostic |

The terminal statuses are `abstraction_complete`, `abstraction_skipped`, and `failed`. Documents in any other status are mid-pipeline and are not yet fully indexed. Retrieval honors `pipeline_status` via the `pipeline_status` filter on `discover` (overridable when a caller specifically wants to query mid-pipeline or failed documents); the default behavior excludes `failed` documents from result sets.

The pipeline-status surface enables three operational patterns. First, callers that ingest documents and then proceed to query against them can poll `get_document` until `pipeline_status` reaches a terminal state, ensuring their queries see fully indexed content. Second, the CAS Application's dashboard reports a count of documents in each status as a vault health indicator. Third, the `sage_reabstract` operation transitions a document's status back to `abstraction_in_progress` and then forward to a terminal state, enabling on-demand regeneration of stale or low-quality abstracts without disturbing the rest of the document record.

# 5. Retrieval Architecture

SAGE provides four retrieval modes, with results scoped by source category and filterable by metadata criteria. Behind the modes, a consistent pipeline runs: filter resolution narrows the candidate set, the content store performs ranking or filter-only enumeration, and salience and abstract-boost adjustments compose with the content score before results are returned. Document-level response shaping (§5.7) is a parameter on the same pipeline. The chain walk operation (§5.9) is a separate primitive over edge chains; it does not run through the discover pipeline and is described on its own terms.

## 5.1 Retrieval Modes

| Mode | Guarantee | Mechanism | Use Case |
|---|---|---|---|
| `semantic` | Approximate; ranked by relevance | Vector similarity search, optionally fused with BM25 keyword matching | Discovery, lessons-learned analysis, context gathering |
| `keyword` | BM25 only | Tantivy full-text index over chunk content | Identifier search, formal terminology, exact phrase matching |
| `deterministic` | Exact content extraction; reproducible; no generation step | Direct content extraction by `document_id` plus heading path; bypasses vector and keyword search entirely | Governed content transfer between documents or agents; verbatim definition or block insertion |
| `catalog` | Filter-only enumeration; no relevance ranking | SQL enumeration over the graph store with metadata filters and configurable sort | Browsing, document-list queries, programmatic enumeration of documents matching criteria |

A few notes on the mode set. Hybrid search (vector plus BM25 fusion) is not a separate mode but a flag on `semantic`. The fusion is performed natively by the LanceDB content store. Hybrid is the default for `semantic` mode because it noticeably improves results on content with defined terminology and formal identifiers, where exact-keyword matching complements semantic similarity.

`Keyword` mode (BM25-only, no vector search) exists for queries where semantic similarity is unhelpful: searching for a known reference number or an exact phrase that should appear verbatim in the source.

`Catalog` mode is fundamentally different from the others: it does not score results by content relevance at all. It enumerates documents that match the filter criteria, returns document-level metadata only (no chunk content), and supports pagination via `offset` and explicit sort via `sort_by` and `sort_order`. The use case is browsing or programmatic enumeration; it would be a misuse to invoke `catalog` mode for a relevance query.

A verification pattern (comparing an authoritative source against a consuming document's usage) is composed by a caller from two `deterministic` retrievals: the caller pulls the authoritative content and the consumer's content and performs the comparison. SAGE does not provide a verification mode because the comparison logic is caller-side; the substrate provides the deterministic-extraction primitive that makes the pattern straightforward.

## 5.2 Source Scope

Source scope controls which documents are eligible for retrieval, independent of mode:

| Scope | Behavior | Implementation |
|---|---|---|
| `all` | Search all documents in the vault | Default; no pre-filtering by scope |
| `authoritative` | Search only documents that are authoritative for the queried domain | Uses `authoritative_for` graph edges to identify eligible source documents |
| `specific` | Search within a named document or set of documents | Direct `document_id` filter |
| `filtered` | Search within documents matching metadata criteria | Pre-filter by `doc_type`, `project`, `lifecycle_status`, `tags`, or `pipeline_status` |

The `filtered` scope deserves additional attention. Document-level metadata filters (everything except `doc_type`) live in the graph store, while content scoring runs in the content store. The retrieval pipeline resolves these filters into a `document_id IN (...)` set against the graph store before the content store ranks chunks. This pre-filter resolution behavior is described in §5.8 and is the reason that `filtered` scope produces the expected result set even when the underlying chunks are concentrated in a small set of documents.

## 5.3 Combined Retrieval Parameters

A typical retrieval call combines mode and scope. Examples:

```
discover(query="normalization", scope="authoritative", mode="deterministic")
```
Returns the exact governed definition from the authoritative source for the queried term.

```
discover(query="normalization approaches", scope="all", mode="semantic")
```
Returns ranked chunks from across the vault, blending vector similarity with BM25 keyword matching when hybrid is enabled (default).

```
discover(query="PV04-CD-002", scope="filtered", filters={doc_type: "claims_draft"}, mode="keyword")
```
Returns chunks from claims-draft documents containing the literal identifier, bypassing semantic similarity entirely.

```
discover(scope="filtered", filters={doc_type: "patent_draft", lifecycle_status: "active"}, mode="catalog", sort_by="document_date", sort_order="desc", offset=0)
```
Enumerates active patent-draft documents in date order, without scoring. Returns document-level metadata only; no chunk content. `Catalog` mode does not require a `query` argument since it does no relevance ranking.

Mode and scope are selected independently, subject to mode-specific constraints noted in each subsection. `Deterministic` mode requires a `specific` scope (a `document_id` plus heading path); `catalog` mode ignores `response_level` because its results are always document-level; `deterministic` mode ignores `response_level` because its results are always chunk-level.

## 5.4 Hybrid Search and Reranking

In `semantic` mode, SAGE supports hybrid retrieval combining vector similarity and BM25 keyword matching via the content store's native fusion capabilities. Hybrid search is valuable when queries contain both natural-language concepts and specific identifiers (for example, "the Normalization definition in the project glossary").

The retrieval pipeline composes content scoring with salience reranking (§5.5) and, when the abstract-boost flag is enabled, abstract-boosted retrieval (§5.6). The composition is loose: each adjustment operates on the document or chunk score independently, and the surface API does not commit to a specific evaluation order. Additional reranking layers (cross-encoder, learned-to-rank) compose at the same boundary without changing the API.

## 5.5 Salience Reranking

Two boosts compose with content scoring in `semantic` and `keyword` modes:

**Active-lifecycle tier sort.** Documents with `lifecycle_status="active"` are placed in tier 0; all other documents are placed in tier 1. The final ordering sorts by tier first and content score second, so an active document always outranks any non-active document regardless of content score. The tier form (rather than a multiplicative score boost) is used because a multiplicative boost can leave a high-scoring archived document outranking a marginally relevant active document, surfacing a stale predecessor over the live successor; the tier sort closes that case at the cost of a slight loss of granularity within the cross-tier comparison.

**Recency boost.** Documents receive up to a 1.10x score multiplier via exponential decay with a 365-day half-life. The date used for decay is the document's `document_date` if present, falling back to `source_modified_at`. Documents with neither receive the baseline (no boost). The recency boost composes multiplicatively with the content score within a tier, so it modulates rank within the active or non-active group without crossing tier boundaries.

The two boosts together produce the default retrieval behavior: active documents surface first, recent documents within the active set float to the top, and content scoring drives the granular ordering inside each tier.

## 5.6 Abstract-Boosted Retrieval

A document's `semantic_abstract` is a generated description of what the document is about (see §3.4.1 stage 3 and the rationale in §2.3). For retrieval, the abstract serves as a document-level relevance prior. With the `use_abstract_prefilter` flag set true (default in `semantic` and `keyword` modes), the retrieval pipeline performs an abstract-match pass against `semantic_abstract` text for documents in scope, and chunks belonging to documents whose abstract matches the query receive a multiplicative score boost during content-store ranking.

Documents without abstracts (vaults where abstraction is disabled, documents with `pipeline_status=abstraction_skipped`, documents whose abstract has not been generated) participate at their natural chunk-relevance scores. They are not penalized; they simply do not receive the abstract boost. A vault that has not enabled abstraction sees no behavioral change from the abstract-boost machinery.

The abstract-boost flag is ignored by `deterministic` and `catalog` modes. Deterministic retrieval is exact content extraction (the abstract is irrelevant); catalog retrieval is filter-only enumeration (there is no relevance score to boost).

CAS-ADR-011 establishes the abstract field on the document record and identifies retrieval as the principal architectural consumer alongside steward orientation and agent triage. CAS-ADR-020 specifies the descriptive third-person prompt framing required for the abstract to function as a relevance-triage card. The two are companion decisions: the field exists because retrieval and agent triage need it, and the prompt is shaped to produce the kind of abstract those consumers can use.

## 5.7 Document-Level Response Mode

Retrieval results can be returned at chunk-level (default) or document-level granularity, controlled by the `response_level` parameter on `DiscoverRequest`:

- `response_level="chunks"` (default). Each hit is a chunk with its `chunk_content`, `heading_path`, parent document metadata, and relevance score.
- `response_level="documents"`. Each hit is a document. Chunk content is suppressed; the chunk's `heading_path` (the location of the best-matching chunk in the document) is preserved as a navigation hint, along with relevance scores and matching-chunk count.

Document-level mode is appropriate when the caller wants to know which documents matched a query without paging through every matching chunk within them. It is particularly useful for orientation queries (where the agent will read the full document or its abstract anyway) and for high-level discovery (showing the user a list of relevant documents to choose from).

The `response_level` parameter applies to `semantic` and `keyword` modes. `catalog` mode is always document-level (it does not return chunks at all). `deterministic` mode is always chunk-level (it returns the specific extracted content; "document-level deterministic" would be a different operation, namely "fetch the whole document," which is what `get_document` provides).

## 5.8 Pre-Filter Resolution

Document-level metadata filters (`lifecycle_status`, `project`, `tags`, `pipeline_status`) and the `document_ids` filter are resolved against the graph store before chunk search runs in the content store. The retrieval pipeline performs an enumeration query against the graph store to collect the set of `document_id` values matching the active filters, and passes this set to the content store as a hard pre-filter on the chunk search.

The pre-filter resolution behavior is required for correctness when a vault has a small population of documents matching the filter relative to the total chunk count. Without it, the LanceDB top-K search might return chunks belonging entirely to documents that the post-filter excludes, producing an empty result set even when many candidate documents satisfy the user's filter. Pre-filter resolution avoids this by forcing the content store to score only chunks belonging to qualifying documents.

Two cases bypass graph-store filter resolution. First, the `doc_type` filter is applied at the content store layer because `doc_type` is denormalized into the chunks schema (§3.3.7); the content store applies it as a SQL `WHERE` predicate against the chunks table during scoring. Second, the `authoritative_for` scope is not a metadata filter but an edge traversal: it walks the `authoritative_for` graph edges to identify the documents authoritative for the queried domain and produces its own `document_id IN (...)` set, which intersects with the document-level filter set produced by graph-store resolution.

When pre-filter resolution produces an empty set (no documents match the active filters), the retrieval pipeline short-circuits without invoking the content store and returns an empty result with `total_before_filtering=0` and `active_filters` populated in the response, so callers can see why the query produced no results.

## 5.9 Chain Walk Operation

The `chain` operation walks an edge chain from any starting document to both ends. Its principal use case is version-history retrieval over `supersedes` chains: given any document in a chain, return the head (current version), the tail (oldest version), and the path between them. The operation works for any edge type, not only `supersedes`; an `instantiated_from` chain or a `derived_from` lineage can be walked the same way.

The operation returns:

- `head_id`: the document at the chain head (downstream end; current version for supersedes chains)
- `tail_id`: the document at the chain tail (upstream end; original version for supersedes chains)
- `query_position`: where the queried document sits in the chain
- `length`: the chain length
- `is_linear`: whether the chain is linear or has forks (forks indicate a malformed chain where chain-repair operations have not yet been applied)

Implementation uses a recursive CTE in the graph store, walking edges of the queried type in both directions from the starting document. The operation is bidirectional and depth-unbounded by design: a caller asking "give me the full history of this document" should not have to specify a depth that turns out to be too small.

`Chain` is distinct from `traverse`. `Traverse` walks the graph from a starting document along edges of one or more types, in a chosen direction, with explicit depth control, returning a tree of reachable documents. `Chain` walks a single edge chain to its endpoints in both directions with no depth limit. The two operations cover different use cases and would not compose cleanly into a single API.

The dedicated `chain` operation makes the fork-detection invariant (`is_linear`) part of the response contract rather than something a caller has to compute from a `traverse` result.

# 6. Access Control and Governance

## 6.1 Design Principle

SAGE enforces data-layer governance: who can read and write documents, and the provenance tracking of who did so. Orchestration concerns (workflow sequencing, agent role assignment, policy-based behavior constraints) belong to the layer above SAGE and are documented in domain-specific instantiations.

## 6.2 User Registration

All actors (human users, agents) are registered in the user table before interacting with SAGE. Registration establishes identity for both provenance and access control. See the User entity definition in §4.2.

## 6.3 Editor-Based Write Control

Default-open: any registered user can read and write any document. Registering one or more editors on a document restricts write operations to the editor set; all others become read-only for that document. "Editor" is the SAGE-layer term for a user designated as a writer on a particular document; it is a per-document role, not a vault-level permission. See the Editor Model in §4.3.

## 6.4 No-Delete Invariant

SAGE never deletes documents. Supersession and archival are the mechanisms for managing document lifecycle. This is a system-level invariant, not a configurable policy. No API operation removes a document record.

The invariant applies to documents only. Edges may be removed via `unlink`, which is the supported mechanism for retracting an erroneous edge or cleaning up after a chain-repair operation. The asymmetry is deliberate: a document represents canonical content with a permanent identity, while an edge represents a relationship claim that can be wrong, refined, or retracted.

## 6.5 Provenance Tracking

Every document records its creator (`created_by`) and the user responsible for the most recent modification. Re-ingestion events record the trigger (the caller that invoked re-ingest) and update `updated_at`. The `metadata_confirmed` boolean (§4.1) tracks whether a document's metadata is caller-authoritative or has been flagged for human review (§3.4.6).

Phase 1 tracks provenance via fields on the document record. A full audit trail with graph edges (`edited_by`, `reviewed_by`) is a Phase 3 consideration relevant when the trust model shifts from a small team to multi-tenant deployment. Decision logs (§4.10) provide a complementary mechanism for capturing operational judgment that does not produce an artifact revision.

## 6.6 Source Authority

The `authoritative_for` edge type identifies which document governs a content domain. This is a graph-level fact, not an agent assignment. Any consumer (human or agent) queries the graph to determine source authority before transferring or modifying governed content.

## 6.7 Blast Radius Assessment

When a change is made to an authoritative document, the graph can compute affected documents by traversing `sync_target` and `references` edges. The assessment produces a report of impacted documents. What an orchestration layer does with the report (block the change, warn the user, auto-propagate) is an orchestration concern. SAGE provides the traversal; it does not enforce the policy.

# 7. Core API Operations

The Core API exposes operations grouped by concern. The grouping mirrors the organization of the OpenAPI specifications: SAGE Core API operations on the URL prefix `/sage_vaults/*` cover graph state, retrieval, ingestion, lifecycle, and access control; CAS Application API operations on the URL prefix `/app/*` cover caller-side workflows that compose SAGE operations into bulk-ingestion pipelines. The two prefixes are architecturally distinct (§3.5.2): the SAGE Core API is the substrate; the Application API is one consumer of that substrate.

This section describes the SAGE Core API surface (§7.1) and the CAS Application API surface (§7.2). The OpenAPI specifications in the Formal Substrate are the canonical contract; this section provides the architectural narrative behind the specifications.

## 7.2 CAS Application API Operations

The Application API at `/app/*` covers caller-side workflows that compose SAGE operations into pipelines. Two endpoints are defined.

| Operation | Purpose |
|---|---|
| `scan(directory, max_depth?)` | Recursive directory walk. Hashes each file (SHA-256), matches the file against the vault's enabled adapters by extension, performs a bulk `hash_check` against the vault's document records to classify each file as `new`, `modified`, or `unchanged`, and returns a structured response including filename-parsed metadata for each file. No state changes |
| `ingest(files, vault_id)` | Per-file SAGE ingest with two-phase edge inference and SSE-streamed progress. Phase 1 (pre-ingest) builds an edge plan from parsed metadata and the existing vault state. Phase 2 (post-ingest) resolves filenames to document_ids, executes Tier 1 links, inserts Tier 2 staging entries, and drops edges for failed ingests. The architectural choice to place `scan` and `ingest` at the Application API rather than the SAGE Core API is deliberate. Filesystem walking, file-hashing, and bulk orchestration are caller-side concerns that vary by deployment context (a CLI tool walks differently from a browser-based application). Placing them in the Core API would commit SAGE to a particular bulk-orchestration model. Keeping them in the Application API preserves SAGE as a request-response state substrate (§3.4.5), with the Application API as one consumer that composes SAGE operations into the workflow appropriate for its context.

The Application API consumes SAGE Core API operations through the same surface that any other client would use. The shared in-memory state under Phase 1's single-process topology (§3.5.2) is an optimization: the Application API backend reads the same vault registry and SAGE service instances that the Core API exposes, but the dependency direction respects the architectural boundary, not the process boundary.

# 8. Multi-Vault Architecture

## 8.1 Vault Isolation Model

SAGE separates knowledge into vaults with clear boundaries. Each vault represents an independent knowledge domain with its own configuration, document types, lifecycle states, and access control policies.

| Concept | Description |
|---|---|
| Organization | Top-level grouping of vaults under a single owner or team |
| Shared vault | Team-visible vault with shared documents and collaborative governance |
| Personal vault | Private vault scoped to one user |
| Vault boundary | Search and graph traversal scoped to one vault |

## 8.2 Cross-Vault Isolation

Each vault has its own content store instance and its own graph store instance. This provides:

- **Content isolation.** Documents in one vault never appear in another vault's search results.
- **Portability.** A vault is a self-contained directory tree. Moving a vault to a different machine or deployment requires no data extraction from shared databases.
- **Governance separation.** Different vaults have different sensitivity profiles and are governed independently.

A SAGE process operates a registry of vaults; each Core API call resolves to a single vault by `vault_id` parameter. SAGE has no cross-vault search, traversal, or join. Users with access to multiple vaults query each independently and synthesize results at the user layer.

## 8.3 Physical Layout

A SAGE vault is a self-contained directory tree at `~/sage_vaults/{vault_id}/`:

| Path | Contents |
|---|---|
| `~/sage_vaults/{vault_id}/vault_config.yaml` | Vault configuration, validated against `vault_config.schema.json` from the Formal Substrate |
| `~/sage_vaults/{vault_id}/brain/` | Database directory holding the graph store and content store |
| `~/sage_vaults/{vault_id}/brain/graph.db` | Graph store (SQLite): document records, edges, lifecycle state, decision log entries |
| `~/sage_vaults/{vault_id}/brain/lancedb/` | Content store (LanceDB): vectors, full-text index, projections, chunk-level metadata |
| `~/sage_vaults/{vault_id}/sources/` | Source files managed by the vault (may be a symlink to external storage such as a cloud-synced directory) |
| `~/sage_vaults/{vault_id}/imports/` | Staging directory for files copied during ingest from outside `storage_root` |

Vault configuration files live outside the SAGE source repository. A reset of the source tree (`git reset`, `git clean`) does not affect vault state. Vault data is operational state, not source-controlled artifact.

The `brain/` and `sources/` separation enables vault portability: moving a vault between machines is a directory copy, with the option to preserve the symlinked sources path on machines that have the same external storage mounted at the expected location.

# 10. Open Design Questions

The items below are identified for future design work. Each item carries an explicit phase or trigger that would prompt resolution.

1. **Provenance edge versus provenance fields.** Phase 1 tracks document provenance via fields on the document record (`created_by`, `updated_at`, plus the lineage carried by `supersedes` edges). A full audit trail with graph edges (`edited_by`, `reviewed_by`) is a Phase 3 consideration, relevant when the trust model shifts from a small team to multi-tenant deployment.

2. **Read-access restrictions.** Phase 1 assumes all registered users can read all documents within a vault. Multi-tenant Phase 3 deployment may require document-level or group-level read restrictions. This consideration pairs with the provenance-edge question: both become relevant when the trust model demands finer-grained governance than vault-level isolation provides.

3. **Periodic LanceDB compaction.** `IngestionService.ingest()` writes a fragment per ingest without compacting; over months of normal ingest activity, fragments accumulate and disk usage grows beyond what the working set requires. A maintenance task or per-N-ingests trigger is warranted. The forward direction is to add a compaction policy that runs as part of vault hygiene without disrupting ingest throughput.

4. **Resolution policies for `sync_target` and `authoritative_for`.** Both are TBD in the edge-type registry (§4.6). `sync_target` may be folded into `references` after evaluation, since the bidirectional-sync semantics may be expressible as paired `references` edges with anchor fields. `authoritative_for` requires its own analysis: the policy choice depends on how authority changes propagate across version chains, which is a question the system has not yet had to answer in practice.

5. **Tags chain inheritance.** Tags are excluded from CAS-ADR-021's chain-inheritance trio because set semantics make "inherit" ambiguous (union, replace, skip are all reasonable defaults). A separate decision will be required if a concrete need surfaces for automatic tag propagation across `supersedes` chains.

6. **Steward and orchestrator decision-log activation.** The schema for decision-log entries (§4.10) is in place. The first consumer (a steward agent in a domain instantiation) awaits a domain choice about which agents accumulate the kind of judgment decision logs are designed to capture. The orchestrator-log surface awaits ROOT Harness implementation, since orchestrator agents do not yet exist.

7. **Editor-endpoint implementation.** The OpenAPI specification declares `set_editors` and `get_editors` (§7.1.7). Implementation is deferred until a calling workflow requires the surface; the editor model operates through the underlying `document_editors` join table for documents that explicitly register editors, but the API entry points are not wired through.

# Appendix A: Agent Consumption Patterns

SAGE provides a graph-queryable state substrate for multi-agent systems. Agents query document metadata, traverse relationships, and check editor permissions before acting. The orchestration logic that determines which agent acts and when is external to SAGE.

In autonomous agent architectures, SAGE serves as the shared state substrate through which agents coordinate. The graph provides the structural knowledge agents need: what documents exist, who has authority, what has changed, and what preconditions must be satisfied. SAGE provides the facts; the orchestration layer provides the judgment.

Three consumption patterns are particularly relevant:

**Discovery and triage.** An agent that has issued a `discover` query receives a result set in which each document carries its `semantic_abstract` (§5.6) alongside core metadata. The abstract is shaped specifically to support agent-side triage: the agent reads the abstract to decide whether to fetch the full document via `get_document`, `read_section`, or `read_projection`. This pattern depends on the descriptive third-person framing of abstracts (CAS-ADR-020); abstracts that are written in the genre or voice of the document they describe are not useful for triage.

**Precondition gating.** An orchestrator dispatching an agent to perform work on a document calls `check_preconditions` first to verify that the document's `depends_on` targets exist and are in valid lifecycle state. The gate is a graph-level fact, not an agent assertion: the orchestrator does not need to know what the work will be in order to decide whether the work can run.

**Authority resolution.** Before transferring or modifying governed content, an agent traverses `authoritative_for` edges to identify the document that governs the relevant content domain, then performs deterministic retrieval against that document. The pattern composes the source-authority machinery (§6.6) with deterministic extraction (§5.1) to produce verbatim governed content with explicit provenance.

The abstraction over these patterns is consistent: SAGE provides the structured state and the primitive operations; the agent or orchestration layer composes them into the workflow appropriate for the task.

Architecture decisions affecting SAGE are maintained in the CAS ADR store (`docs/cas_adr_store.json`), a separate source authority shared across the CAS portfolio. The following CAS ADRs affect this document. See the CAS ADR store for full context, options considered, rationale, and consequences.

**CAS-ADR-001: LangGraph as ROOT Harness orchestration engine** (accepted, 2026-03-16). Establishes the boundary rule: LangGraph nodes call SAGE Core API for all state queries and mutations. Resolves SAGE's open design question on agent orchestration framework.

**CAS-ADR-002: Separation of SAGE, ROOT Harness, and domain instantiation documents** (superseded by CAS-ADR-005, 2026-03-16). Established three-layer document separation with PIM as a ROOT Harness appendix.

**CAS-ADR-005: PIM Health Instantiation as independent document** (accepted, 2026-03-16). Supersedes CAS-ADR-002. PIM documentation is fully independent; SAGE carries no domain-specific content.

**CAS-ADR-007: CAS: Clif's Agentic System as portfolio umbrella name** (accepted, 2026-03-16). SAGE is the memory component within the CAS portfolio.

**CAS-ADR-008: Formal substrate as independent CAS artifact** (accepted, 2026-03-16). SAGE's Core API contracts, object model schemas, lifecycle state machine definitions, edge type taxonomy validators, and vault configuration schemas are specified in the CAS Formal Substrate artifact.

**CAS-ADR-011: Semantic abstract generation at ingestion** (accepted, 2026-03-30). The ingestion pipeline runs three stages (projection, indexing, abstraction). The abstraction stage generates a density-proportional semantic abstract via a local LLM. The document record carries a `semantic_abstract` field; the edge schema carries a `rationale` field. Retrieval, steward orientation, and agent triage are the architectural consumers of the abstract.

**CAS-ADR-012: Decision logs as SAGE-managed steward and orchestrator companion artifacts** (accepted, 2026-03-30). Stewards and orchestrators may each own an append-only decision log capturing operational judgment that does not produce an artifact revision. Three categories: decisions not to act, decisions deferred, cross-artifact reasoning. Schema is part of the Formal Substrate.

**CAS-ADR-014: Named Core API operations replacing organize()** (accepted, 2026-03-30). The Core API exposes `set_lifecycle()` for lifecycle transitions and `update_metadata()` for metadata mutation as separately named operations. Direct policy enforcement gates by operation name rather than by parameter inspection. The Core API and the Formal Substrate's policy schema use the same operation names.

**CAS-ADR-015: Metadata extraction is a SAGE-level capability, not a caller responsibility** (accepted, 2026-04-16). FilenameParser is part of `sage/services/`, so filename-based extraction runs uniformly across all ingestion entry points. The extraction precedence chain runs caller-supplied > filename parse > adapter projection, with the default-to-`misc` doc_type fallback firing only when none yield a value.

**CAS-ADR-016: SAGE normalizes UI-layer file metadata on ingest** (accepted, 2026-04-16). On macOS, files copied into the vault from outside `storage_root` are stripped of UI-invisibility markers (BSD UF_HIDDEN chflag, com.apple.FinderInfo invisible bit) so canonical artifacts remain user-auditable. No-op on non-macOS platforms.

**CAS-ADR-017: Chain-scoped edge resolution with anchor and retraction primitives** (accepted, 2026-04-18). Each edge type declares a `resolution_policy` from a four-valued enumeration. Edges carry two nullable anchor fields (`source_valid_from_version`, `target_valid_from_version`) governed by a write-time invariant keyed on policy. Retractions are first-class edges (`retracts`) targeting the retracted edge instance; chain merges are marked by a first-class `merged_from` edge with `valid_until_version` tombstoning on predecessor-chain edges. Edge-type registry lives in SAGE core, not vault configuration. See Appendix D for a worked example.

**CAS-ADR-018: Ingestion is exclusively intentional; SAGE provides no file watcher or auto-ingest** (accepted, 2026-04-25). Documents enter SAGE only when a caller explicitly invokes an ingest operation. Source change detection is tied to explicit re-ingest via content-hash comparison, with a `supersedes`-linked successor created on detected change. The source-adapters schema does not include a `watch_paths` field; SAGE provides no watcher process, polling loop, or scheduled scan.

**CAS-ADR-019: Auto edge inference may delete its own prior edges to repair chains; hand-curated edges are protected by a provenance gate** (proposed, 2026-04-29). Auto-inferred `supersedes` edges carry a `[version_chain]` rationale prefix. Chain-repair operations may remove auto-inferred edges to repair chains when a versioned arrival shifts the desired chain shape; if any candidate-removal edge is hand-curated, the entire group's repair downgrades to Tier 2 staging. Group-level downgrade preserves the coherence of the proposed repair.

**CAS-ADR-020: Abstract generation prompt: descriptive framing for agent relevance triage** (accepted, 2026-05-01). The semantic-abstract generation prompt is shaped for agent-side triage: descriptive third-person voice, `doc_type` as a parameterized input, anti-fabrication clauses, no genre-instantiation. Generation runs under greedy decoding for deterministic output. The `AbstractionProvider.generate_abstract` interface accepts a `doc_type` parameter threaded from the document record through the ingestion service to the provider.

**CAS-ADR-021: Metadata inference and review are caller responsibilities; SAGE accepts authoritative values** (accepted, 2026-05-01). `IngestRequest.needs_review: bool` defaults to `false`: SAGE commits caller-supplied metadata as authoritative and skips filename inference. With `needs_review=true`, SAGE marks `metadata_confirmed=false` and may invoke filename inference for fields the caller did not supply. Chain-inheritance exception: when `supersedes_document_id` is set, the predecessor's `doc_type`, `project`, and `authority_scope` are read and applied per-field if the caller did not supply them. Review semantics are caller-driven; vault-level review configuration is not part of the schema.

**Candidate ADRs sequenced for drafting alongside this revision:**

**CAS-ADR-022 (candidate): Documentation maintained as a SAGE vault with supersedes-edge version history.** CAS reference documents become content within a SAGE vault dedicated to the CAS portfolio, with version history captured via `supersedes` chains rather than git diffs. New revisions produce new files with bumped version labels; the vault carries the lineage.

**CAS-ADR-023 (candidate): Linear supersedes chain.** Each version supersedes only its immediate actual predecessor in the chain, not all prior versions. Linear chain semantics simplify the resolver, prevent the edge count from growing as the square of chain length, and align with the natural mental model of version history.

# Appendix D: Worked Example, Chain-Scoped Edge Resolution

This appendix walks through a representative case of how the chain-scoped resolution primitives compose: anchor fields, retraction edges, merge tombstones, and the resolver's behavior at query time. The example illustrates the model described in §4.5, §4.6, and §4.7.

**Setup.** Two independent supersedes chains exist in the vault:

- Chain A, with versions a1, a2, ..., a9, where each version supersedes the one before it.
- Chain B, with versions b1, b2, ..., b5, where each version supersedes the one before it.

The chains advance independently. Each `supersedes` edge carries `resolution_policy: none` (per the meta-edge convention in §4.6) and no anchor fields.

The notation `(aN, bN)` used below denotes the conceptual evaluation position of the resolver: aN is the query position on chain A, bN is the query position on chain B. A `traverse` API call takes a single starting document; the two-position notation is shorthand for describing where on each chain the query effectively sits during the resolver's evaluation.

**Time T1: a covers edge is introduced.** A `covers` edge is created from chain A to chain B. The `covers` edge type carries `resolution_policy: transitive_both` in the registry, so the edge requires both anchors. The reviewer authoring the edge sets `source_valid_from_version = a3` and `target_valid_from_version = b2`. The semantic claim: "from a3 onward in chain A, that chain covers chain B from b2 onward."

The edge row in the graph store carries:
- `source_id = a3` (the version on chain A at which the relationship was authored)
- `target_id = b2` (the version on chain B at which the relationship was authored)
- `edge_type = covers`
- `resolution_policy = transitive_both` (frozen at creation from the registry)
- `source_valid_from_version = a3`
- `target_valid_from_version = b2`

Resolver behavior: a query at position `(a5, b3)` walks the graph from `a5`, finds the covers edge, and checks the anchors. Source position `a5` is downstream of `a3` in chain A's supersedes lineage (a5 supersedes a4 supersedes a3 by chain advancement), so the source anchor is satisfied. Target position `b3` is downstream of `b2` similarly, so the target anchor is satisfied. The edge surfaces. The resolver emits an `anchor_hit` event in the resolution-path debug payload.

**Time T2: a retraction is introduced.** A reviewer determines that the covers edge ceases to apply from chain A's perspective starting at version a7. The reviewer authors a `retracts` edge. The `retracts` edge type carries `resolution_policy: none` and is anchored on the retracting chain. The edge row carries:

- `source_id = null` (retracts edges target an edge instance, not a document)
- `target_id = null`
- `edge_type = retracts`
- `resolution_policy = none`
- `retracted_edge_id = <id of the covers edge from T1>`
- `source_valid_from_version = a7` (the chain A version from which the retraction takes effect)
- `target_valid_from_version = null` (one-sided: retraction applies from chain A's side)

Resolver behavior at three query positions:

- Query at `(a8, b4)`. The resolver walks from `a8`, locates the covers edge from T1, checks its anchors (both satisfied as before), then checks for retractions. It finds the `retracts` edge with `retracted_edge_id` matching the covers edge's id. The retracts is anchored on chain A at `a7`; query position `a8` is downstream of `a7`, so the retraction applies. The covers edge is excluded from the result. The resolver emits a `retracts_applied` event.

- Query at `(a6, b3)`. The resolver locates the covers edge, checks anchors (satisfied), then checks for retractions. The retracts is anchored at `a7`, but query position `a6` is upstream of `a7` (a6 is older than a7). The retraction does not apply at this query position. The covers edge surfaces. Resolution-path debug payload shows `anchor_hit` followed by no `retracts_applied`.

- Query at `(a8, b4)` from chain B's side. A query starting from `b4` looking for inbound `covers` edges does NOT apply the retraction. The retraction is anchored on chain A and represents chain A's governance action; it applies only when the resolver evaluates the edge from the retracting chain's side. Chain B's view of the edge is unaffected: the covers edge surfaces as if no retraction existed. This one-sidedness is intentional and matches the semantics of governance retraction: chain A unilaterally retracts its claim to cover chain B, but chain B has no basis to consider itself "uncovered" without its own retraction.

**Time T3: chain A merges into chain C.** A new chain C is created with c1 as its first version. The merge is marked by a `merged_from` edge from c1 to a9 (the terminal version of chain A). The merge produces two effects in the edge data:

- A new edge row is created: `source_id = c1`, `target_id = a9`, `edge_type = merged_from`, `resolution_policy = none`. This is the chain-level provenance record.
- The covers edge from T1 has its `valid_until_version` field set to `a9` (the terminal predecessor version). The covers edge is tombstoned for any query starting from chain C: the terminal `a9` represents the end of chain A's relevance for chain C.

Resolver behavior:

- Query at `c2` on chain C. The resolver does not walk through `merged_from` edges to discover edges on the predecessor chain; `merged_from` records chain-level provenance but is not a propagation path for resolution. The covers edge from T1 lives on chain A and is reachable only by queries on chain A's lineage. The `valid_until_version = a9` marker is the explicit tombstone that forecloses any backdoor inheritance: even a resolver that did attempt to walk through the merge would find the covers edge tombstoned at a9 and would not surface it for query positions on chain C. The covers edge does not surface from c2; the resolver emits a `tombstone_applied` event. There is no covers edge on chain C until someone explicitly re-attaches one through tooling (auto-migration is forbidden by the architecture; see CAS-ADR-017).

- Query at `(a8, b4)` on chain A directly. The covers edge still applies along chain A's own lineage (subject to the retraction at a7). The merged_from / tombstone affect only queries that start on chain C and walk through the merge.

**Summary of primitives.** The example exercises the full set of chain-scoped resolution mechanisms:

- Anchor fields (`source_valid_from_version`, `target_valid_from_version`) declare the version range over which an edge applies on each chain.
- The write-time invariant keyed on `resolution_policy` ensures that anchor populations match the policy declared in the registry.
- `retracts` edges, anchored on the retracting chain, mark edges as retracted from a specific version forward without mutating the original edge.
- `merged_from` edges record chain-level provenance for chain merges.
- `valid_until_version` tombstones predecessor-chain edges at a merge point, preventing automatic propagation across the merge while keeping the original edges queryable for time-travel.
- The resolver consults the edge-type registry, evaluates anchors, applies retractions and tombstones, and emits a structured `resolution_path` debug payload that exposes each evaluation event.

These five primitives compose to express version-specific facts (the meta-edges), one-sided chain-to-stable relationships (`derived_from` and similar), and chain-to-chain claims that persist across version turnover (the transitive-both group), while preserving an audit trail through retraction and tombstoning rather than destructive mutation.
