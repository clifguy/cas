# Candidate ADRs CAS-ADR-022 and CAS-ADR-023

**Date:** 2026-05-06
**Status:** Draft for review before merge into `docs/cas_adr_store.json`
**Drafted by:** Cowork session 2026-05-06 (sage_arch_v2 work stream)

These two candidate ADRs are surfaced by the SAGE Architecture Reference v2.0 rewrite. CAS-ADR-022 captures the meta-architectural decision made in this session about how CAS reference documents are versioned and stored. CAS-ADR-023 captures the linear-supersedes-chain invariant that governs the supersedes-edge graph shape across all SAGE vaults.

Three other candidates surfaced earlier in the session (sequential ingestion pipeline, lazy abstraction model loading, single-process Phase 1 topology) were reclassified as deployment-environment constraints rather than architectural decisions and moved to `2026-05-06_deployment-notes-source-material.md` for incorporation into the Deployment Model rewrite. The architectural-vs-deployment test that drove the reclassification: an architectural decision is portable across deployment environments, while a deployment-environment constraint is driven by the specific resources of a particular deployment and would change with different resources.

The drafts use the `docs/cas_adr_store.json` schema. After review and any revisions, each draft is merged into the JSON store with status set per the schema's `accepted` enumeration.

## CAS-ADR-022: Documentation maintained as a SAGE vault with supersedes-edge version history

**Status:** proposed
**Date:** 2026-05-06
**Scope:** cross_cutting
**Tags:** [documentation, sage-vault, version-control, dogfooding]
**Affects:** CAS Overview, SAGE Architecture Reference, ROOT Harness Architecture Reference, Deployment Model, CAS Application Spec, Formatting Standards, Project Tracker
**Created by:** Clif

### Context

The CAS portfolio includes a set of reference documents (CAS Overview, SAGE Architecture Reference, ROOT Harness Architecture Reference, Deployment Model, CAS Application Spec, Formatting Standards) and operational artifacts (Project Tracker, ADR Store). The reference documents are maintained as `.docx` files in the repository's `docs/ref/` directory. Version history is carried by a versioned-filename convention (e.g., `_v1_4_2.docx`) plus git history.

This pattern works at the scale of a single developer reading and editing the documents directly. It creates frictions at scale or with agent participation: (1) cross-document retrieval (e.g., finding which reference documents discuss the abstraction model) requires manual search rather than SAGE's existing retrieval surface; (2) document lineage between versions is implicit in filenames rather than queryable graph relationships; (3) the documents are not available to agents through the same MCP tools that agents use to consult the working corpus; (4) the version-bump-and-rename workflow is manual, with format and naming inconsistencies accruing.

SAGE is a knowledge infrastructure system designed for exactly this kind of structured document state with version lineage. Using SAGE for CAS's own documentation aligns with the principle that the system should manage what it is good at managing.

### Options considered

**Option 1: Status quo.** Continue with `.docx` files in `docs/ref/` and versioned-filename conventions. Pros: no migration work, no new infrastructure. Cons: the frictions above persist; the documents remain unavailable to agents through SAGE; cross-document retrieval requires external tooling.

**Option 2: External documentation system.** Move CAS reference documents to Obsidian, Confluence, or another documentation platform. Pros: mature tooling for documentation workflows. Cons: introduces a parallel knowledge substrate alongside SAGE; documents are not available to agents through SAGE's MCP surface; cross-system synchronization is its own ongoing burden.

**Option 3: Documentation as content within a SAGE vault.** Provision a SAGE vault dedicated to the CAS portfolio. Reference documents become documents in the vault, with `supersedes` edges expressing version lineage. Pros: existing infrastructure; CAS reference documents are retrievable through SAGE's standard surface; agents can consult them via MCP; the system uses what it specifies. Cons: new vault provisioning work; migration of existing `.docx` files into the vault; alignment of the file-naming convention with vault ingestion.

**Option 4: Hybrid.** Continue maintaining `.docx` files in the repository and additionally ingest them into a SAGE vault. Pros: preserves existing workflow while adding SAGE retrieval. Cons: two sources of truth that can drift; ingestion is not the canonical representation; reverse changes from vault back to repo files are awkward.

### Decision

CAS reference documents are maintained as content within a SAGE vault dedicated to the CAS portfolio. Each document's version history is captured via `supersedes` edges in the vault's graph store rather than via filename versioning plus git history. New revisions produce new files with bumped version labels; ingest creates a `supersedes` edge from the new version's document record to the prior version's record.

The vault is provisioned at `~/sage_vaults/cas/` with a `vault_config.yaml` declaring the relevant domain vocabulary (`architecture_reference`, `app_spec`, `deployment_model`, `formatting_standards`, `project_tracker`, `overview`, `worked_example`). The vault is configured for intentional ingest, with caller-authoritative metadata via `needs_review=false` (per CAS-ADR-021); revisions are committed via explicit ingest invocations rather than file-watcher detection.

The CAS Project Tracker, which is updated near-continuously, also lives in the vault as a tracked document with a long `supersedes` chain. The CAS ADR Store (`docs/cas_adr_store.json`) remains in the git repository because it is structured data consumed by code (validators, ADR-lookup tooling) rather than narrative content for human or agent reading. The Formal Substrate (`docs/fs/`) likewise remains in the repository as operational artifact consumed by code.

### Rationale

SAGE is purpose-built for graph-structured document state with version lineage. The CAS reference document set is exactly the kind of corpus that SAGE manages well: typed documents with version chains, cross-document references, and the need for both retrieval and structural queries. Storing the documents in SAGE practices what the architecture specifies and exercises the system on its own canonical content.

The format-follows-access-pattern principle informs the boundary. Reference documents are narrative content read by humans and agents and benefit from SAGE's retrieval, abstract-boost, and traversal capabilities. The ADR store is structured data consumed by validators and tooling and benefits from JSON Schema validation and direct programmatic access; ingestion into SAGE would not improve those access patterns. The Formal Substrate (schemas, OpenAPI specs) is similarly operational artifact for code consumption.

The decision aligns with two earlier architectural choices. CAS-ADR-008 separates the Formal Substrate from the architecture documents because they have different access patterns (code-consumed vs. human-read). The same reasoning applied here separates narrative documentation (vault-resident) from structured data (repository-resident). CAS-ADR-005 establishes that PIM Health domain instantiation is a separate document; the same modularity applies to CAS portfolio documentation, which lives in its own vault rather than alongside SAGE source code.

### Consequences

- A new SAGE vault `cas` is provisioned at `~/sage_vaults/cas/` with a `vault_config.yaml` declaring CAS-portfolio document types and the standard SAGE document lifecycle.
- The CAS reference documents are ingested into the `cas` vault. Migration creates `supersedes` chains for documents with multiple existing versions (e.g., SAGE Architecture Reference v1.0 → v1.1 → v1.2 → v1.3 → v1.4 → v2.0).
- The `docs/ref/` directory in the repository transitions to a vault-sources directory or is removed once migration completes; final state is that `docs/ref/` no longer holds canonical document copies.
- Each future document refresh produces a new `.docx` file with a bumped version label and is ingested via `sage_ingest` with the predecessor's `document_id` supplied as `supersedes_document_id`.
- The CAS Project Tracker becomes a vault-resident document with frequent supersedes chain entries. Agents and humans consult it via MCP retrieval rather than git checkout.
- The CAS ADR Store remains at `docs/cas_adr_store.json` in the repository. The Formal Substrate remains at `docs/fs/`. Both are operational artifacts consumed by code.
- Cross-document retrieval across CAS reference documents becomes a SAGE query. Agent-side reasoning about CAS architecture can consult the documents through MCP rather than requiring out-of-band file access.
- The `cas` vault's MCP exposure makes CAS portfolio documentation accessible to any AI client connected to the SAGE MCP server, alongside the working PIM Health vault and any other vaults.
- A formatting-standards entry in the new vault declares the conventions that future document refreshes should observe.

## CAS-ADR-023: Linear supersedes chain

**Status:** proposed
**Date:** 2026-05-06
**Scope:** sage
**Tags:** [graph, supersedes, version-chain, edge-inference]
**Affects:** SAGE Architecture Reference, CAS Application Spec, Test Plan
**Created by:** Clif

### Context

The `supersedes` edge type expresses version lineage. When a document is superseded by a newer version, an edge is created from the new version to the prior version. SAGE creates `supersedes` edges in two paths: manual ingestion (caller supplies `supersedes_document_id` on `IngestRequest`) and bulk-ingest auto-inference (version-detection from filename version codes, per CAS-ADR-019).

For a document that has gone through multiple versions (v1, v2, v3, ...), there are two architecturally meaningful chain shapes the supersedes graph could take:

**Linear chain.** Each version supersedes only its immediate actual predecessor. v3 supersedes v2; v2 supersedes v1; no edge from v3 directly to v1. The chain is a single path from the head (current version) to the tail (oldest version) through `supersedes` edges.

**Exhaustive chain.** Each version supersedes all prior versions. v3 supersedes v2 and v1; v2 supersedes v1. The chain is a complete graph among all version members.

Both shapes are valid graph topologies. The choice has implications for: (1) edge count growth as chains lengthen; (2) chain-walk algorithms for version-history retrieval; (3) the resolver's transitive lookup for chain-scoped edge resolution per CAS-ADR-017.

The behavior of chain-scoped edge resolution depends on the supersedes structure. The resolver walks supersedes lineage to identify chain membership for transitive resolution. A linear chain is straightforward to walk: each version has at most one predecessor and one successor. An exhaustive chain has multiple incoming and outgoing supersedes edges per version, complicating the lineage walk.

### Options considered

**Option 1: Linear chain.** Each version supersedes only its immediate actual predecessor. Pros: edge count scales linearly (N edges for a chain of length N+1); resolver lineage walk is simple; matches the natural mental model of version evolution. Cons: querying "all prior versions of v3" requires a recursive walk rather than a direct query.

**Option 2: Exhaustive chain.** Each version supersedes all prior versions. Pros: querying "all prior versions of v3" is a single-hop query (return all targets of v3's outbound supersedes edges). Cons: edge count scales quadratically (N(N+1)/2 edges for a chain of length N+1); the resolver's lineage walk has to choose among multiple successors; chain-repair operations are more complex; mental model is awkward (does v3 "supersede" v1 directly, or transitively through v2?).

**Option 3: Configurable per-vault.** Vaults choose linear or exhaustive based on their workload. Pros: flexibility. Cons: graph semantics should be consistent across vaults; cross-vault tooling (chain-walk operations, chain-repair logic, the resolver itself) would have to handle both shapes; the choice between shapes is not actually domain-dependent.

### Decision

The supersedes chain is linear by construction. Each version supersedes only its immediate actual predecessor. v3 supersedes v2; v2 supersedes v1; there is no edge from v3 directly to v1. This applies uniformly across all SAGE vaults; it is not a vault-configurable property.

Both creation paths uphold the linear-chain invariant. The bulk-ingest auto-inference engine (per CAS-ADR-019) emits one supersedes edge per chain-adjacent version pair. Manual ingestion via `IngestRequest.supersedes_document_id` accepts a single predecessor id; callers wishing to express that a new version replaces multiple prior versions do so by creating the chain link to the immediate predecessor and walking the chain to identify all prior versions.

The dedicated `chain` operation (described in SAGE Architecture Reference §5.9) provides a single API call that walks a linear supersedes chain to both ends from any starting position. Its return shape includes an `is_linear` boolean as a sanity check on the chain's topology.

### Rationale

Linear chain has three reinforcing benefits.

First, edge count scales linearly with chain length. For a vault with hundreds of documents and chains reaching v10 or beyond, the difference between linear (N edges) and exhaustive (N(N+1)/2 edges) is substantial. A vault with many long chains under exhaustive semantics has a quadratically growing edge count, which affects storage, traversal cost, and the resolver's working set.

Second, the linear chain matches the natural mental model of version evolution. When a reviewer thinks about "v3 supersedes v2," the meaning is that v3 replaced v2 directly. The exhaustive shape requires the reviewer to mentally decide whether v3 also "supersedes" v1, which is logically true but semantically redundant.

Third, the resolver's transitive lookup for chain-scoped edge resolution (per CAS-ADR-017) walks supersedes edges to identify chain membership. A linear chain is simpler to walk and easier to reason about: each version has at most one predecessor and one successor through supersedes. An exhaustive shape would require the resolver to deduplicate or special-case multi-edge cases, complicating the implementation and the reasoning about its correctness.

The cost is that querying "all prior versions of document v3" requires a recursive walk rather than a single-hop query. This is acceptable for three reasons: (1) version-history queries are an occasional operation, not a hot path; (2) the recursive walk is supported natively by SQLite's recursive CTE, the same mechanism used for `traverse` and `chain`; (3) the dedicated `chain` operation centralizes the walk in a single Core API endpoint with `is_linear` as a sanity-check field, so callers do not have to implement chain-walking logic themselves.

Option 3 (per-vault configuration) was considered and rejected. Graph semantics should be consistent across vaults to enable cross-vault tooling. The edge-type registry lives in SAGE core (per CAS-ADR-017) for the same reason; the supersedes-chain shape is a similarly substrate-level invariant that benefits from being uniform.

### Consequences

- Auto-inferred supersedes chains during bulk ingest are linear: each new versioned document supersedes only its immediate predecessor.
- Chain-repair operations preserve the linear invariant: when a chain is repaired (out-of-order arrival shifts the desired chain shape, per CAS-ADR-019), the result is a linear chain. The repair removes any edges that would produce a non-linear shape.
- The `chain` operation walks the linear chain in both directions and returns `is_linear: true` for well-formed chains. A return of `is_linear: false` indicates a malformed graph requiring chain-repair.
- Querying "all versions of document X" walks the chain via recursive CTE. The cost is logarithmic in chain length for a single forward or backward walk and linear for a full chain traversal; the cost is acceptable for occasional version-history queries.
- The `IngestRequest.supersedes_document_id` validator accepts a single predecessor id. Multi-predecessor supersession is not supported by direct API; callers needing it use chain-repair tooling.
- The CAS Application's edge-review surface expects linear chains; non-linear chains surface as anomalies for reviewer attention.
- Cross-vault tooling (chain walks, chain-repair, the resolver itself) can rely on the linear-chain invariant being uniform across vaults.
- Test coverage: chain-shape tests in `tests/sage/test_traverse_anchors.py` and `tests/app/test_batch_ingest_service.py` cover linear-chain behavior under chain repair, out-of-order arrival, and the `is_linear` sanity check.
