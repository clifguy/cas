A CAS-owned review pass for **Azure deployment surfaces**. It catches the class of failure that is expensive precisely because it is invisible to ordinary gates: a change that passes the linter, the unit tests, the IaC compile, and CI, yet is wrong — and is discovered only after a 15–40 minute build → deploy → converge → preflight cycle. The catalog below is distilled from real Azure-deploy failures; it is the judgment layer on top of whatever deterministic gates a repo already has.

This procedure carries the complete failure-mode catalog. Resolve the CAS binding and current project authority before executing it; its generic Azure failure mechanisms do not authorize another project deployment.

## When to invoke

Run it on any diff that touches a deployment surface:

- **IaC** — `infra/**`, `*.bicep`, `*.bicepparam`, ARM JSON, APIM policy XML.
- **CI/CD** — `.github/workflows/**` deploy and build pipelines.
- **Bootstrap / preflight** — container entrypoints, managed-identity or database bootstrap scripts, deploy preflight scripts.
- **Dependency closure / image inputs** — `pyproject.toml`, `uv.lock`, `requirements*.txt`, `Dockerfile*`, or any commit that adds a new runtime import or system-binary dependency. These can open a **local↔cloud parity gap** (a capability present on the workstation but absent from the deployed image) even when no `infra/` or workflow file changes — so a diff that changes what the runtime image must contain is in scope even if it touches only application code and its dependencies (see AD5, the local↔cloud parity entry).

If the diff touches none of these, return "no deploy surface in scope" and stop. For application code-correctness, defer to the repo's own code-review skill.

## The spine: on a deploy surface, green is not proof

The defining property of this catalog (AD1) is that **for many deploy-surface changes, no source-level or static check can establish correctness** — the behavior is produced by a deploy-time transform or a live-resource fact that the local toolchain does not reproduce. For those changes:

- A passing source-asserting test is **not evidence of correctness**. A test that pins the *post-transform source form* of such a construct is worse than nothing: it cannot fail when the deployed form is wrong, and it freezes the (possibly broken) source shape as "correct."
- The gate of record is the **live deploy plus inspection of the transformed artifact** — the stored APIM policy, the actual role assignment, the running revision.
- The reviewer's job is therefore not to "verify" these changes at the source, but to (a) recognize the class, (b) demand live-deploy proof, and (c) catch the smells that predict a non-fix.

Sections AD2–AD5 are the cases where something *can* be caught early.

---

## AD1 — Non-local verification (deploy-only-verifiable change)

**What this catches.** A change whose correctness depends on a deploy-time transform or a live-resource fact the local toolchain does not reproduce — often dressed up with a source-level test that "proves" it.

**Review prompts.**
- Does the change's effect pass through a transform the local build does not run? Example: an XML/string payload that survives `loadTextContent` → ARM JSON → service parse, where entity escaping mutates (a source `&quot;` can land as `&amp;quot;`); a value templated through several IaC layers.
- Does correctness depend on a *live-resource* fact — a server-side function existing on a particular database/connection, a role assignment, a DNS or certificate binding, a revision being healthy? None of these are observable from source.
- Is the diff adding a test that asserts the **source form** of such a construct? Flag it as **false confidence** — recommend deleting it or replacing it with a deploy-time assertion that inspects the transformed artifact.
- Does the change claim to *fix* a defect that was only ever seen on deploy? Then its proof must be a live deploy, not a green CI run — say so explicitly.

**What "correct" looks like.** Where feasible, the round-trip-fragile construct is *removed* rather than escaped-just-so (e.g., move an inline-quoted policy condition into its own operation-scoped policy so no fragile string survives the round-trip). Where the fact is live-only, the change carries a note that it is verified against a live deploy + an artifact inspection, not a source test.

## AD2 — False-green CI/deploy step

**What this catches.** A pipeline job or step that **skips or no-ops yet reports success**, so the run is green while the work never ran.

**Should be a deterministic gate.** This class is statically checkable; prefer a CI test over a review prompt where the repo can host one.

**Review prompts.**
- Does a job-level `if:` reference `vars.*` or a context not in scope at that level? GitHub does **not** expose *environment-scoped* variables to a job-level `if` (only repo/org vars) — an env-scoped `vars.X` there is always empty, so the job silently skips and the run stays green. (Real instance: a `deploy` job gated on an env-scoped `AZURE_CLIENT_ID` skipped every dispatch and reported success.)
- Does a step run `what-if`/plan with no corresponding `apply`, or a conditional `apply` that can be silently false?
- Does any step swallow a non-zero exit (`|| true`, a missing `set -e`, a background process whose failure is unwatched)?
- Does "success" assert an *effect* (a resource changed, a probe passed), or merely that a command returned 0?
- Does a new gate assert something the **deployed artifact emits unconditionally**, while the condition it protects lives in tenant/directory state the gate never reads? This is the adjacent case to a skipping step: the gate *runs* and asserts an effect — just not the load-bearing one, so it is green on precisely the tenant where the prerequisite is missing. Name the state the gate cannot see (a role's `allowedMemberTypes`, an identifier URI, a consent grant, a CORS response header) and say what it would have to probe to see it. (Real instances: a preflight check asserting the grant types an APIM policy serves, while whether any machine principal can actually obtain a token lives in Entra; an edge advertising an OAuth resource identity that no pipeline step ever registers.)

**What "correct" looks like.** What decides whether real work runs is the dispatch event + the environment binding + the auth step — not a variable invisible at the gate's scope. A green run corresponds to work actually performed, asserted by a post-step probe that reads the state the change depends on — not one that reads the artifact the change ships.

## AD3 — Misdiagnosis / non-fix recurrence

**What this catches.** A "fix" that addresses an error's surface form rather than its cause — the kind that passes every gate and recurs on the next deploy.

**Review prompts.**
- Does the fix target the *wording* of an error (e.g., add a type cast because the message said "unknown type") rather than a confirmed root cause? Name the confirmed cause; if it is not established, flag the fix as speculative.
- Is this change a **re-fix** of a symptom a previous commit already claimed to fix? A recurrence means the prior fix was a non-fix; the new one needs live-deploy proof before it is trusted.
- Does the diagnosis rest on a hypothesis the local toolchain cannot test? Then it is unproven until the deploy runs.
- Does the commit argue that a change is **safe** on deploy (ordering, coupling, rollback) rather than that it is a fix? Verify the mechanism the argument rests on — that the two artifacts genuinely ship together, that the file is genuinely copied into the image, that the rollback path genuinely exists. A false safety argument passes every gate exactly like a false fix, and reads as more trustworthy because it sounds cautious. (Real instance: "seed and image ship from the same commit, so forward deploy is coupled and safe" — where the seed file was referenced only by a manually-run bootstrap script and reached no image or workflow at all.)

**What "correct" looks like.** The commit states the confirmed root cause (not the symptom), and — for a deploy-only-verifiable cause — defers the "fixed" claim until a live deploy confirms it. A safety argument names the mechanism that makes it safe, in terms someone can check against the repository.

## AD4 — Managed-identity / role-grant gap

**What this catches.** A runtime identity that authenticates but is **not authorized** — a 401/403 on healthy infrastructure because a token or managed identity lacks the role, app-role, scope, or grant it needs.

**Review prompts.**
- Does the change introduce a new caller→resource hop (app MI → database, deploy SP → API, preflight token → resource server, app MI → Graph / SharePoint / Key Vault)? Is the corresponding grant created in the same change (RBAC role assignment, Entra app-role, database `GRANT`, Key Vault access policy)?
- For a token minted with an explicit `--resource`/audience: does the principal carry the *app-role* that resource requires, or does it only authenticate? Authentication ≠ authorization.
- For a privileged operation (admin-only function, directory write): is it called from a principal scoped for it, against the right resource/database?
- Is least privilege preserved (no over-broad admin role granted to dodge a missing narrow grant)?

**What "correct" looks like.** Every new identity→resource hop ships with its grant in the same diff, scoped to the minimum the call requires. A 401/403 on a healthy edge points here first.

## AD5 — Azure platform-scoping gotcha catalog (living)

**What this catches.** The accumulating set of "this Azure resource behaves differently than the source implies" facts. Each entry is a generic rule plus the instance that taught it. **This section grows by one entry every time a new gotcha is hit, in any app.**

- **Postgres Flexible Server `pgaadauth_*` (and other admin functions) exist only in the built-in `postgres` maintenance database.** Calling them on the application database raises `UndefinedFunction` despite the correct signature. Connect to `postgres` for principal/role creation; keep app-DB work (extensions, schema) on the app connection.
- **APIM policy XML round-trips re-escape entities.** A `loadTextContent`'d policy's `&quot;` / `&amp;` can double-encode through ARM. Prefer operation-scoped policies with no inline-quoted string conditions over a catch-all policy that depends on a fragile inline condition. Verify against the `format=xml` stored policy, never the source.
- **APIM policy XML comments forbid a literal `--` (and cannot end in `-`).** A prose em-dash typed as `" -- "` inside `<!-- ... -->` parses fine as text and passes Bicep `what-if`/validate (which treats the policy as an opaque `loadTextContent` string), but APIM's own XML parser rejects it at deploy time with `An XML comment cannot contain '--'`. Write a real em-dash (`—`) or rephrase to avoid the dash; verify with an actual XML parse (`xml.etree.ElementTree`/`lxml`), not a grep for `--`, since that string also appears legitimately in the comment delimiters themselves. *Two policy files added in the DCR-compatibility facade change used `" -- "` as an em-dash substitute in prose comments; a cor-prod deploy's Bicep apply failed the APIM sub-deployment on both. Distinct from the entity-re-escaping gotcha above — this is an invalid character sequence inside the comment body, not an entity round-trip.*
- **GitHub environment-scoped `vars.*` are invisible to a job-level `if`.** (See AD2.)
- **ACA scale-to-zero adds cold-start latency** that can fail a tight post-deploy probe; pin a warm minimum replica for anything a preflight hits immediately, and/or give probes a cold-start budget.
- **Managed-identity authorization is separate from authentication.** (See AD4.)
- **Container-app health is revision-local.** A `000`/no-response from one app while its sibling answers and DNS resolves points at that app's revision health, not at ingress or DNS.
- **`az account get-access-token --resource <aud>` always mints a v1 token** (`iss=https://sts.windows.net/<tid>/`, `ver=1.0`) and **ignores the resource app registration's `requestedAccessTokenVersion`** — that setting governs only the v2 `--scope <aud>/.default` endpoint. So a v2-validating edge (APIM `validate-jwt` / a backend whose issuer is `…/v2.0`) rejects the `--resource` token at the edge. The fix has **two required parts**: mint via `--scope <aud>/.default` *and* set the resource app to `requestedAccessTokenVersion: 2`; either alone is a non-fix (the `--scope` move yields v2 only if the resource app is v2, and the app-reg setting does nothing for `--resource`). Separately, `--scope .../.default` is authorization-bearing — it requests the caller's app-roles on the resource — so a principal that minted fine under `--resource` (authentication-only) can now fail to mint, or mint a roleless token the backend 401s (see AD4). *Cost a cor-prod deploy cycle; "set the app reg to v2 alone" was a documented non-fix because `--resource` ignores it.*
- **ACA's `WorkingSetBytes` / `MemoryPercentage` metrics undercount mmap'd, file-backed memory.** They omit file-backed page-cache pages, so a process that memory-maps large on-disk artifacts (e.g. ML model weights loaded from disk) reports a memory metric far below its true resident set. Size such a container from the measured process RSS, not the cloud memory metric — otherwise it is under-provisioned and OOM-killed (exit 137) at a limit the metric reported as comfortable. *A SAGE container sat well under its 1 GiB limit by the metric yet was SIGKILLed loading the embedding model at startup; the loaded model (~1.1 GiB resident, ~1.6 GiB transient peak) plus a worst-case embed batch (~2.5 GiB RSS) never showed in `WorkingSetBytes`. Cost a cor-prod deploy cycle.*
- **The MCP Python SDK (`FastMCP`) auto-enables DNS-rebinding Host validation, returning HTTP `421` (`Invalid Host header`) for any non-loopback `Host` — i.e. every request that arrives through a proxy.** When the server's bind `host` is a loopback value (`127.0.0.1`/`localhost`/`::1` — the default), `FastMCP` turns on `TransportSecuritySettings(enable_dns_rebinding_protection=True, allowed_hosts=['127.0.0.1:*','localhost:*','[::1]:*'])`. Mounted behind APIM/ACA, every authenticated request carries the edge `Host`, not a loopback one, so the MCP SSE handshake (`GET /mcp/sse`) is rejected at `connect_sse` with `421 Invalid Host header` while plain REST on the same app is unaffected. **The trap (AD1): a `TestClient`/in-process probe sends a loopback `Host` by default, lands on the allow-list, and returns 200 — so the failure is invisible to every in-process test and appears only once a real non-loopback `Host` traverses the edge.** Fix by passing explicit `transport_security` that disables rebinding protection on the HTTP-mounted MCP surfaces (the public-edge boundary is the JWT/identity layer, not a browser-localhost threat model); the regression test must send a non-loopback `Host` and assert the handshake is not 421. This is **independent of the ingress `transport`**: `transport: auto`/HTTP-2 does *not* break SSE — SSE needs no HTTP/1.1 Upgrade; only WebSocket does, which is what microsoft/azure-container-apps#280 is actually about. *A SAGE MCP-over-HTTP SSE surface (`GET /mcp/sse`, `GET /mcp_admin/sse`) returned 421 through APIM while every REST path returned 200/401 in the same preflight run; first misdiagnosed as the ingress transport — a non-fix that pinned `transport: 'http'` and left the 421 unchanged — then proven in-process to be FastMCP's Host validation (`status=421 body='Invalid Host header'` against a non-loopback Host through the real mounted `sse_app()`). Cost two cor-prod deploy cycles.*
- **GitHub Actions step-only contexts (`runner`, `steps`, `job`) are invalid in a workflow-level or job-level `env:`.** Only `github`, `needs`, `vars`, `inputs`, `secrets`, `strategy`, and `matrix` are in scope for a job/workflow `env:`; a `${{ runner.* }}` (e.g. `runner.temp`) there makes the whole workflow unparseable and GitHub rejects the dispatch with `HTTP 422 — Unrecognized named-value`. **The trap (AD1/AD2): a PyYAML-based structural test parses `${{ runner.temp }}` as a literal string and passes, and a `workflow_dispatch`-only workflow is never dispatched by the pytest CI job, so the error is invisible to every pre-merge gate and surfaces only on a real dispatch.** Fix by using a job-env-valid context (`github.workspace` for a path) or moving the value into a step. Statically checkable — promote to a deterministic gate that scans every workflow's workflow/job-level `env:` for step-only contexts. *A SharePoint vault-source validation workflow set `SP_VALIDATE_STATE_FILE: ${{ runner.temp }}/…` in job env; every dispatch 422'd and the harness never ran, past a green structural test, green CI, and two clean review passes — merged broken, caught only at the first live dispatch, then refixed the same session with a repo-wide gate.*

- **APIM `validate-jwt` runs on the CORS preflight `OPTIONS`, so a browser-context client is blocked before it can authenticate.** A `validate-jwt` in the inbound pipeline 401s the preflight `OPTIONS` a browser sends ahead of any cross-origin call (it carries no token yet) and returns no `Access-Control-Allow-*` headers, so the browser blocks the real request — while a non-browser caller (curl, a server-side OAuth client) sends no preflight and connects fine. **The trap (AD1): every source-level check and every non-browser client passes; the failure appears only for a real browser-context client (an OAuth flow in a renderer — Codex Desktop, a Codex.ai connector) and only against the live edge.** Fix by adding a `<cors>` policy AHEAD of `validate-jwt` so the preflight short-circuits anonymously; a preflight `OPTIONS` matches the catch-all operation, so one API-level `<cors>` answers every path's preflight — but a dedicated operation that omits `<base/>` (an anonymous `/register` or `.well-known/*`) needs its own `<cors>` for its *actual* response to carry `Access-Control-Allow-Origin`. Verify with an `OPTIONS` probe returning 2xx + `Access-Control-Allow-*` (promote to a preflight gate) and a real browser-context client end to end. *A cor-prod SAGE edge 401'd `OPTIONS /register` and `OPTIONS /mcp` while `POST /register` returned 201 and authenticated `/mcp` worked; the DCR facade built for standards-default (browser-context) MCP clients was non-functional for exactly that client class, invisible to every curl-based probe until the first real Codex Desktop connection failed.*

- **An ARM `Microsoft.Insights/diagnosticSettings` with `GatewayLogs` enabled only *routes* the logs APIM emits — it does not make APIM *emit* them.** A `diagnosticSettings` resource is a destination binding: it wires a category to a workspace/sink, but APIM produces its own gateway request/response logs only when a service-level `Microsoft.ApiManagement/service/diagnostics` (instance name `azuremonitor`) **and** a `Microsoft.ApiManagement/service/loggers` child (`loggerType: 'azureMonitor'`) both exist. Azure Monitor *platform metrics* emit unconditionally, which masks the gap: `AzureMetrics` fills (the workspace visibly "has APIM data") while `AzureDiagnostics` / `ApiManagementGatewayLogs` stay empty across every category. **The trap (AD1): nothing at the source or in CI shows it — the `diagnosticSettings` compiles, `what-if` shows it created, and metrics confirm the workspace is wired; only a live Log Analytics query for the log tables (or an `az resource list` that shows no logger/diagnostic children under the service) reveals the empty logs.** Ship the `azureMonitor` logger + `azuremonitor` service diagnostic in the same change as the `diagnosticSettings`, and verify with a post-traffic `ApiManagementGatewayLogs`/`AzureDiagnostics` query — never a metrics query, which is green regardless. *A cor-prod APIM shipped with a `GatewayLogs`-enabled `diagnosticSettings` and correct-looking wiring; metrics flowed but every resource-log category stayed empty 2 h after traffic, and `az resource list` showed no logger or diagnostic child resources — the setting was routing logs the service had never been told to emit. Cost a deploy cycle; fixed by provisioning the `azureMonitor` logger + `azuremonitor` diagnostic in `infra/modules/apim.bicep`.*

- **`az ad app permission admin-consent` returns exit 0 but does not create the delegated consent grant for a first-party Microsoft Graph scope (e.g. `offline_access`, and likely `openid`/`profile`/`email`).** The permission is *requested* (`az ad app permission add … --api <graph> --api-permissions <scope>=Scope`) and admin-consent reports success, yet no `oauth2PermissionGrant` for that Graph scope is created — `az ad app permission list-grants --id <client>` shows only the pre-existing resource-app scopes. The scope is advertised and requestable but unconsented, so Entra issues no refresh token and the client re-authorizes every access-token lifetime. Fix by following the `permission add` with an explicit `az ad app permission grant --id <client> --api <graph-app-id> --scope <scope>`, which records an `AllPrincipals` grant; resolve Graph's app id at run time so no GUID literal is baked in. **The trap (AD1): the consent is a live directory fact — a source/structural test can only assert the script *carries* the grant command; the grant itself is proven on a live bootstrap (`list-grants` shows the `oauth2PermissionGrant`) or an end-to-end client sign-in that receives a refresh token, never in CI.** Verification quirk: `GET /servicePrincipals/{graph-sp}/oauth2PermissionGrants` lists grants where Graph is the *client*, not grants *to* clients on Graph — use `az ad app permission list-grants --id <client>` to read a client's own consents. *A cor-prod bootstrap requested and admin-consented `offline_access` on a public MCP client but left it unconsented (verified live: admin-consent exited 0 while `list-grants` showed only the resource scope); the tenant was remediated by hand with the explicit grant, then the bootstrap script was codified to match and a preflight check added to assert the advertisement. The admin-consent-only version shipped first as a non-fix. Cost a deploy/remediation cycle.*

- **A wrong built-in role-definition GUID in a Bicep/ARM `roleAssignments.roleDefinitionId` passes `what-if`/validate but fails the *apply* with `RoleDefinitionDoesNotExist`.** Neither Bicep validation nor `what-if` resolves the role-definition id against the live directory, so a misremembered or mistyped built-in-role GUID — even one correctly wrapped in `subscriptionResourceId('Microsoft.Authorization/roleDefinitions', <guid>)` — is invisible until the apply, where ARM rejects it with `RoleDefinitionDoesNotExist: The specified role definition with ID '<guid>' does not exist` and aborts the whole sub-deployment. A mirrored-allowlist test (a Bicep literal that must equal a test literal) does NOT catch this: it asserts the two copies agree, not that the value is a real role, so a wrong GUID written into both sides passes green. **The trap (AD1): the GUID is a plausible-looking constant — a near-miss differing only in the final segment reads as correct to every source check, the allowlist gate, and the what-if pass; only the live apply resolves it.** Verify a built-in-role GUID against the authoritative source (`az role definition list --name '<Role Name>' --query '[0].name' -o tsv`), never from memory. *A cor-prod deploy of an APIM Application Insights telemetry plane carried `3913510d-42f4-4e42-8a64-420c390d0215` for Monitoring Metrics Publisher (the real id ends `…420c390055eb`) — a from-memory constant never checked live; Bicep validate/what-if and a mirrored allowlist test were all green, and the apply failed the `apim` sub-deployment with `RoleDefinitionDoesNotExist`, aborting before the bootstrap and preflight steps ever ran. Fixed by correcting the GUID against a live `az role definition list` lookup. Cost a deploy cycle.*

- **`az containerapp job start` with *any* container-override flag (`--env-vars`, `--image`, `--command`, …) rebuilds the execution's `containers[0]` from the flags alone — it does not patch the deployed job template.** Supplying only `--env-vars` (the common case: thread a per-invocation request into a one-shot job) drops everything the flags do not restate: the image (so the execution fails validation with `(ContainerAppImageRequired) Container with name '<job>' must have an 'Image' property specified` before any code runs), the baked `command` (and a re-passed `--command "python -m foo.bar"` lands as a single bogus token `["python -m foo.bar"]`, not `["python","-m","foo.bar"]`, so the container fails to exec), the baked env, and the container name (which becomes the job name — breaking a later `az containerapp job logs show` that omits `--container`). A sibling job that starts with **no** override flag inherits the template intact, which is why one one-shot job works and another does not. **The fix is set-env-then-start-plain:** `az containerapp job update -n <job> -g <rg> --set-env-vars "${VARS[@]}"` (a *merge* — baked coordinates survive; `--replace-env-vars` would not) followed by a plain `az containerapp job start -n <job> -g <rg>` that inherits the full deployed template plus the just-set request. Serialize the update→start pair (a per-tenant `concurrency` group suffices) so a second dispatch cannot interleave; the request env then persists in the job definition until the next run or a redeploy overwrites it (harmless — each run sets its own). Also pass `--container <name>` to any failure-path `az containerapp job logs show`. **The trap (AD1): a structural test can only assert the *workflow source shape* (update present, no override flag on start); the container-spec-drop is a live Azure CLI behavior no local toolchain reproduces, so the proof is a live dispatch reaching `Succeeded`, not a green CI run — and the load-bearing fact to confirm there is that `--set-env-vars` merges rather than replaces.** *A cor-prod SAGE maintenance workflow started its in-VNet job with `az containerapp job start --env-vars`; all four out-of-band operations (vault teardown, document purge) failed at the first dispatch with `ContainerAppImageRequired` before any maintenance code ran, while the sibling postgres-bootstrap job — which starts with no `--env-vars` — worked. The broken pattern entered with the original teardown workflow and was carried into the generalized maintenance workflow; caught by a live smoke test, fixed by update-then-plain-start. Cost a deploy-verification cycle.*

- **Local↔cloud dependency parity: a capability present on the workstation but absent from the built image fails only in the cloud.** Any runtime dependency the app acquires — a Python package (e.g. `aiohttp`, pulled in by the async managed-identity credential), a system binary (`pg_dump`; `tesseract`/`ghostscript` for OCR), a model or data file — must be added to the *cloud image's* build closure (the `pyproject.toml`/`uv.lock` extra it installs under, the Dockerfile apt/pip layer) in the **same change** that introduces the dependency — not just to the local environment, which often carries it out-of-band. **The trap (AD1): local runs pass because the workstation has the tool; the gap manifests only against the deployed image or edge.** Crucially, these are introduced by *dependency-adding commits that may touch no `infra/`/workflow file*, so invoke this skill on dependency-closure changes (`pyproject.toml`, `uv.lock`, `Dockerfile`, a new import) — not only on IaC diffs (see When to invoke). **Should be a deterministic gate:** assert the built image's closure covers every declared runtime capability (a capability probe on the image, e.g. OCR; the Dockerfile-vs-Bicep client-major match below), so a capability added without its image dependency reds a fast gate. *Seen three times: an omitted async-HTTP dependency crashed the cloud app on boot; an absent `pg_dump` halted a cloud database teardown; an omitted OCR toolchain silently disabled scanned-document ingest in the cloud — each invisible to every local run, each a deploy-verification cycle. A specific `pg_dump` instance follows.*

- **`pg_dump`/`pg_restore` refuse a server whose major version exceeds the client's, so a container image that shells out to `pg_dump` against an Azure Database for PostgreSQL Flexible Server must ship a `postgresql-client` whose major is ≥ the server major.** An older client aborts with `server version: <N>.x; pg_dump version: <M>.x; aborting because of server version mismatch`, and an *absent* client aborts earlier still with `[Errno 2] No such file or directory: 'pg_dump'`. The stock `postgresql-client` in a `python:*-slim` / Debian-Ubuntu base is frequently an *older* major than the Flexible Server (e.g. bookworm ships client 15 against a server pinned to 16), so the naive `apt-get install postgresql-client` is a non-fix — add the PGDG apt repo and pin `postgresql-client-<major>` to the server major, reading the distro codename from `/etc/os-release` so the layer survives a base-image bump. **The trap (AD1): this is a build-plus-runtime fact no source check reproduces. A structural test that asserts the Dockerfile *text* installs a client is a drift guard, not a correctness proof; the real proofs are a container smoke that runs `pg_dump --version` in the built image (asserting the expected major on `PATH`) and the live database operation against the real server.** Bind the pinned client major to the IaC-declared server major — parse `postgresVersion` out of the Postgres Bicep and assert the Dockerfile installs `postgresql-client-<that major>` — so a future server-version bump that forgets the image reds a fast gate instead of a deploy. **Should be a deterministic gate:** the Dockerfile-vs-Bicep major-match assertion and the `pg_dump --version` container smoke are both statically/CI-checkable and belong in the repo. *A SAGE runtime image shipped no `postgresql-client` at all, so the cloud `delete_vault` maintenance teardown's snapshot-before-destroy `pg_dump` raised `[Errno 2] No such file or directory: 'pg_dump'` and the snapshot-halt safety envelope correctly aborted every default-snapshot apply before dropping anything; even had the binary been present, Debian stock's older client would have refused the major-16 Flexible Server. Found only by a post-deploy cloud smoke — the local workstation had `pg_dump`, so it was invisible to every local run. Fixed by installing `postgresql-client-16` from the PGDG repo in the runtime stage, pinned to the Bicep server major with an anti-drift structural gate plus a container smoke asserting `pg_dump` on `PATH` at 16. Cost a deploy-verification cycle.*

## This is early-warning, not a substitute for the deploy

By construction (AD1), this skill cannot make a deploy-only-verifiable change *provably correct* before the pipeline runs — that proof exists only on the live deploy. What it does is cut the rate of merged non-fixes and front-load the recurring Azure gotchas so a new app does not rediscover them one slow deploy cycle at a time. The strongest entries (AD2, and parts of AD4/AD5) should be promoted to deterministic CI gates in each repo; this skill is the judgment layer and the catalog of record.

## Growing the catalog

A pattern earns a place here once it has cost a real deploy cycle and has a confirmed cause (the same bar a good failure log uses). Add it to the most specific applicable section; when a gotcha is statically checkable, also land a deterministic gate in the repo and note it under "Should be a deterministic gate."

## Out of scope

- Application code-correctness, style, naming — the repo's own code-review and linters own these.
- Generic security review — a dedicated security skill covers it.
- The deploy itself — running it and reading the preflight is the gate of record, not this review.
