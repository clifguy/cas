# Archived source genealogy — not execution instructions

## §16 Notes on the genealogy

This skill codifies lessons from the first batched cohort dispatches in CAS:

- **<ticket-id>** projection-point closure follow-up, dispatched 2026-05-21 (9 tickets, inaugural).
- **<ticket-id>/<ticket-id>/<ticket-id>** dispatched 2026-05-23.
- **<ticket-id> + <ticket-id>** sage admin docstring cohort, dispatched 2026-05-25 (foundation-ticket pattern's first appearance).

Live lessons (landing-model-independent, or reframed for the v2.0.0 PR model):

- **Queue-based landing** (v2.4.0). `/merge` v0.8.0 stopped rebasing and force-pushing: under a merge queue the queue builds and tests the merged tree itself, so a per-landing rebase is redundant and costs a force-push plus a second full CI cycle. Three consequences for `/batch`. Serial landing is still the discipline, but for a *content* reason (foundation-first) rather than a mechanical one — the queue would order entries regardless. A stale branch now surfaces as a `CONFLICT` or `BEHIND` halt instead of a rebase conflict inside `/merge`, so §11's mechanical resolution fires from a different signal while its cadence is unchanged. And the dispatcher's own rebase work is untouched: `/batch` still rebases in the worktree under an authorized policy, which is now the only place a rebase happens at all.
- **PR-based landing model** (v2.0.0). `/batch` was realigned with the PR-based landing model adopted by `/plan` (v0.2.0+), `/commit` (v0.2.x), and `/merge` (v0.2.x). The dispatcher no longer cherry-picks worktree branches onto a local `main`; instead each subagent commits→pushes→opens a draft PR, and the dispatcher lands each PR via `/merge` (rebase + squash) behind a second structural gate. This shed roughly half the v1.0.0 body — the entire local-landing engine — to `/commit` and `/merge`. The superseded local-landing notes are preserved in §16.1.

- **Decision sheet as persisted artifact** (<ticket-id>). The first cohort produced an ephemeral plan; mid-dispatch revisions had no canonical home. Subsequent cohorts persist the decision sheet so future audits can read it and so a second cohort can build on it.

- **Pilot before fanning out** (<ticket-id>, reframed in v2.0.0). Validate the *mechanism* once before committing the whole cohort to it. Under v2.0.0 the pilot validates the full PR chain end-to-end (plan → commit/push/PR → merge), not just the first commit. (The original v1.0.0 anecdote — a second subagent's worktree branching from a pre-first-commit state and diverging — is a cherry-pick-era artifact; see §16.1.)

- **Worktree isolation, reframed** (<ticket-id>, reframed in v2.0.0). Worktree isolation is still real, but under the PR model the worktree branch *becomes the PR branch* — it is no longer something the dispatcher lands on main locally. The defense shifts from "absorb forced isolation via cherry-pick" to "let `/plan` own provisioning so the branch is correctly named, and key `/merge` off the subagent-reported branch." See §6.3, the branch-name linchpin.

- **Mechanical-resolution policy as authorized pattern** (<ticket-id>, reframed in v2.0.0). The propose→authorize→apply→verify→retire cadence survives, but its venue moved: from resolving a cherry-pick conflict inside the dispatch loop to resolving a *rebase* conflict after `/merge` halts. `/merge` stays categorically strict and never auto-resolves; `/batch` applies the authorized rule in the worktree, then re-pushes and re-invokes `/merge` (§11, seam option (c)). A single-commit guard (§11) keeps the rebase-replay hazard out of scope. The PR model makes mechanical resolution *more* defensible than the local model did, because CI on each PR is a second safety net the local touched-test run never had — but the first-occurrence human-authorization gate stays; never auto-resolve an unseen shape.

- **Disjoint-edit-window invariant** (<ticket-id> + <ticket-id>, named in v1.0.0, elevated in v2.0.0). The conceptual heart of why cohort batching works: every ticket's edit window is disjoint from every other ticket's. Under v1.0.0 a violation produced a recoverable cherry-pick conflict; today it produces a conflict that halts `/merge`, which refuses both to auto-resolve and to update the branch. The invariant is therefore the cohort's *primary* conflict-prevention guarantee, not merely the success mode — §11 is the recovery net behind it, not a substitute. §4.3 names it as a planning lever and falsification test.

- **Foundation-ticket pattern** (<ticket-id> + <ticket-id>, first instance). When the cohort needs DRY treatment of a shared region, one foundation ticket establishes the content and downstream tickets cross-reference. Required: explicit scope split (foundation touches ONLY shared site; consumers touch ONLY per-tool sites) and foundation-first order — under v2.0.0 the foundation PR merges before consumer PRs rebase onto it. §4.4 codifies the pattern.

- **Push discipline, inverted** (<ticket-id>, inverted in v2.0.0). Under v1.0.0 the dispatcher withheld the push entirely — "cohort on local main, surface for review; push is the user's explicit decision." Under v2.0.0 the push is no longer withheld: it moves into each subagent's `/commit` (push + draft PR). The human gate didn't disappear — it relocated one step later, from "push" to "squash-merge," enforced by the §9 MERGE GATE. §13.4 reports merge state, not a held-back push.

- **Close-ticket is human-gated** (<ticket-id> and <ticket-id>/<ticket-id>/<ticket-id>, structurally enforced since the predecessor skills). The user's standing workflow gates are: code → review → commit → merge → close, with the later steps user-gated. Subagents stop at `/commit` (draft PR open); the dispatcher stops at `/merge` (`ready_for_close`); the user runs `/close-ticket <ticket-id>` per ticket explicitly. `/merge` shares this exact gate.

- **Two-skill split was wrong** (v1.0.0). v0.2.0 of `/plan-batch` split into `/plan-batch` + `/dispatch-batch` on the hypothesis that dispatch would add too many tokens to a planning session's context. Empirically, dispatch added negligible tokens because subagents fully encapsulate execution and the dispatcher only sees small status reports. Meanwhile, the session boundary's real value — the approval pause between plan-locked and dispatch-firing — was being violated by agents blowing through both skills in one go. v1.0.0 merged back into `/batch` with a structural turn boundary (the DISPATCH GATE) that defeats the blow-through failure mode. v2.0.0 adds a symmetric second boundary (the MERGE GATE) so the irreversible squash-merge is also gated. The dispatcher prompt as a serialized artifact is gone — the planner-dispatcher renders the per-ticket subagent prompt in-flight from the decision sheet and the §8.2 template.

- **TaskCreate system reminders are noise** (<ticket-id>). The dispatcher session received the "task tools haven't been used recently" reminder many times. Ignore these — the queue lives in dispatch state, not TaskList.

- **Anti-yield subagent discipline** (read-response-contract cohort, 2026-05-31). A pilot subagent backgrounded the full `tests/sage/` suite and then waited for a completion notification, yielding the turn; the harness cannot resume a yielded foreground subagent, so the work stranded complete-but-uncommitted and the dispatcher had to reconstruct state from the worktree to finish `/commit`. The mitigation, applied ad hoc that run, is now the durable default: the §8.2 template forbids backgrounding the suite or waiting on a notification (affected files only, foreground; CI is the full-suite backstop), and §12.3 codifies the worktree-inspection recovery for when a subagent yields anyway.

- **Flaky-vs-real CI discrimination** (read-response-contract cohort; surfaced at the <ticket-id> pilot, 2026-05-31). `/merge`'s wait loop halts on any CI `FAILURE`. During that cohort a check failed and passed on the *identical* commit SHA — flakiness, not a real break — and the dispatcher hand-ran `gh run rerun --failed` before re-entering the wait. §10.3 codifies that maneuver as a bounded seam in `/batch`'s merge loop: test for flakiness (same-SHA `SUCCESS` evidence, or a known-flaky-list hit held in §8.1 state), rerun once if flaky, halt as before if real. The seam lives in `/batch`, not `/merge` — mirroring the §11 boundary so `/merge` stays categorically strict and flaky-unaware. Complementary to <ticket-id>, which de-flaked the recurring check (`test_reabstract_background_sets_failed_on_error`) at the source.

### §16.1 Superseded landing-model notes (v1.0.0 local cherry-pick)

These lessons described the v1.0.0 local-landing machine — the dispatcher absorbing each subagent worktree onto a local `main` via fast-forward or cherry-pick. **That machine no longer runs in `/batch`.** The mechanics it describes have either moved to `/merge` or been eliminated by the PR model. They are preserved here for audit continuity — the cohort history that produced them is real — and as forward-pointers to where the responsibility now lives.

- **Pilot-divergence anecdote** (<ticket-id>). Under the v1.0.0 local-landing model, the first cohort dispatched two subagents in quick succession before discovering that worktree isolation was forced; the second subagent's worktree branched from a pre-first-commit state and diverged. Under the PR model this specific divergence cannot occur the same way — each subagent opens an independent PR, and the merge queue builds it against the current default branch. The *general* lesson (pilot the mechanism once) is retained, live, in §16.

- **Mechanical-resolution as a dispatch-loop cherry-pick fixup** (<ticket-id>). Under the v1.0.0 model the dispatcher resolved cherry-pick conflicts inline in the dispatch loop. The propose→authorize→apply pattern is retained but its venue moved to post-`/merge`-halt rebase fixup — see the live, reframed lesson in §16 and the mechanics in §11. *(Prevention shifts upstream: §4.3 disjoint-edit-window invariant.)*

- **Cherry-pick is the typical post-pilot path** (<ticket-id> + <ticket-id>). Under the v1.0.0 model, 9 of 9 post-pilot subagents in the 2026-05-25 cohort spawned worktrees forked from planning-session-start; fast-forward failed deterministically and cherry-pick was the landing path. Under the PR model there is no cherry-pick at all — fork-staleness is absorbed by the merge queue. Purely historical.

- **Branch-deletion flag depends on landing path** (<ticket-id> + <ticket-id>). Under the v1.0.0 model, after a fast-forward merge `git branch -d` succeeded, but after a cherry-pick `-d` correctly refused (original sha unreachable from main) and `-D` was required. *This reasoning now lives in `/merge` Step 8*, which deletes the squash-merged branch with `-D` for the identical reason (squash-merge ≈ cherry-pick: the landed sha differs from the branch sha). Nothing left for `/batch` to own. → `/merge` Step 8.

- **Locked worktree teardown — unconditional unlock** (<ticket-id>, validated 2026-05-25). Under the v1.0.0 model the dispatcher unlocked each harness-locked agent worktree before removing it. *Teardown now lives in `/merge` Step 8.* → `/merge` Step 8. (Note: whether `/merge`'s teardown clears a still-locked agent worktree under the current harness is a `/merge` correctness question, tracked separately from this skill.)
